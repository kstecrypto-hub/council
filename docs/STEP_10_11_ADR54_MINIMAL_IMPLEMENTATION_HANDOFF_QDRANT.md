# ADR-54 — Steps 10 and 11: minimal implementation handoff, Docker containment, and Qdrant long-term RAG

**Owner-approved design direction: October 21, 2026.** **Scope:** implementation-ready MVP policy for Steps 10 and 11, without reopening already-approved Steps 5, 7, 8, 9, ADR-49/50/52/53, or imposing a new supervisory service. **Status: SPECIFICATION APPROVED ONLY.** No Docker/network implementation, Qdrant collection, SQL migration, integration, provider call, runtime test, or security verification has been performed. Implementation agents choose ordinary engineering details and demonstrate the required behaviors; no claim of production readiness.

## Step 10 — normal Docker lifecycle with an enforced outbound boundary

1. **Keep the existing shared, trusted Council connector/MCP broker.** Models propose typed tool calls; they do not connect directly to MCP servers or receive raw provider/service credentials. MCP tools can contact their **specifically authorized outside services** as their purpose requires; the trusted broker validates caller, tool, external target, permissions, account, effect and current authorization. A tool is not implicitly allowed arbitrary onward internet access.
2. **Enforce containment rather than assuming it from the connector.** A sandbox-local child process, Python, curl, package manager, DNS client or newly created worker could otherwise originate its own network traffic outside the tool path. Put the member Docker sandbox on an actually egress-denied/restricted network where it can reach only the narrowly approved internal Council execution/tool bridge, not arbitrary outside destinations or the Docker host/daemon. The trusted bridge/MCP service, outside the untrusted sandbox, separately enforces authorized outbound destinations. Prevent host networking, arbitrary extra interfaces/routes and access to Docker socket/privileged mounts. Native trusted model inference and Council internal database/host/snapshot duties keep their existing separate paths. Deny-first enforcement must be tested, not just stated in prompts.
3. **Use ordinary Docker containers and existing Step 7 rules.** Each member has its isolated, persistent named volume/approved mount and private workspace; restart or recreate attaches the same verified volume, but does not pretend to restore a worker process's RAM. The whole-member scheduler handles start/stop, budget/epoch/UNKNOWN reconciliation, checkpoint/PAUSED/BUDGET_EXHAUSTED gates and finite infrastructure recovery. No per-worker restart manager or new queues.
4. **Resource allocation:** discover actual machine capacity, reserve host OS/Docker/WSL/storage and applicable GPU headroom first, then divide usable capacity fairly across **currently admitted active** member sandboxes. Adjust concurrency or shares when resources are scarce; never allocate all physical resources to containers. Respect existing configurable Step 7/8 Docker/cgroups CPU/RAM/PID hard bounds and outside-container monitoring (initial 2–5 second samples, ~80%/~90% assigned-memory pressure actions, ~20% host-RAM reserve adjusted to measurements). Monitor host/WSL2, disk and optional GPU/VRAM separately. Cannot guarantee that OOM or machine failure is impossible: react safely and preserve recovery truth.
5. **External sandbox checker:** outside the container mechanically validates correct logical member/epoch/status, intended image and persistent mount identity/ownership, branch scope, CPU/RAM/PID limits, host/network/DNS egress denial with a negative direct-access probe, approved internal bridge reachability, absence of Docker socket/secrets, and any applicable frozen-checkpoint permissions. It reports actual PASS/FAIL/UNKNOWN per check; failed or unverified required checks block admission/re-admission. It does **not** grade the agent's code. Rebuild candidate environment from pinned definitions before declaring reproducibility.
6. Implementation choices (Docker networking/firewall mechanism, exact typed DTOs, thresholds tuned to host, mount naming, probes) are left to the responsible agent, while the above observable behavior is fixed.

## Step 11 — current-run graph/continuation as designed; Qdrant for archived cross-project knowledge

1. **No redesign of existing current-run memory.** The canonical typed evidence graph remains PostgreSQL-backed with source/version relationships. Each member has bounded normal working memory, already-designed context manifests, continuation packets, private workspace and ADR-52 provider-interruption recovery. Step 5/7 operation/authorization/UNKNOWN truth wins over model summaries.
2. **Agent-driven retrieval:** make scoped graph-query and source/history-search tools visible in the member's instructions. Let the member choose relevant graph neighborhoods on demand, especially newer **relevant** changes since its last seen event/graph watermark at restoration, project milestones and checkpoint preparation. Do not blindly inject the whole graph, force a retrieval after every trivial tool call, or assume the newest unrelated graph node is useful. Enforce member and checkpoint visibility at query and result delivery.
3. **Archive every project to the extent authorized, preserving actual outcome.** At project completion/closure, prepare a customer-owned versioned, content-hashed archival export of permitted graph findings/edges, significant and ordinary logged actions/attempt outcomes, decisions, experiments, frozen artifacts and references, whether the result succeeded, failed or was incomplete. Preserve the full authorized action/evidence history in the Git-backed archive/artifact store, **not as one embedding per action**. Do not label untested work as successful, silently retain disallowed customer data, or export private branch data to other customers.
4. **One post-project LLM summarization/selection pass when approved:** create a concise project-level summary plus selected significant decisions, observations, lessons, working approaches and context-specific failures. Mark selected significant actions separately from underlying mechanical receipts and link each summary/lesson to actual source IDs, archived Git commit/artifact hashes, versions, outcomes and tested conditions. This summary is a derived interpretation, never canonical proof.
5. **Qdrant is the selected vector database for long-term RAG.** Store vectors plus source-linked metadata for these selected summaries/lessons in a scoped, private Qdrant collection/index, using its vector search indexes (e.g. HNSW) and indexed payload filters for tenant, source, project/version, retention and outcome. **No pgvector/PostgreSQL vector search for this RAG layer.** Qdrant is a replaceable/rebuildable retrieval index over the authorized Git-backed archival records, not the canonical live Council operation/evidence database. Its lifecycle/backup/deletion follows customer ownership and authorization. Avoid creating new general-purpose memory databases/supervisors beyond this explicit Qdrant long-term retrieval role.
6. **Embedding efficiency:** index selected reusable chunks, not every raw event; deduplicate by content hash and embedding-model/version; persist embedding outputs and only embed new or changed chunks. Qdrant's HNSW/payload indexing makes retrieval efficient, **not embedding generation free**. Embeddings still require local compute, a hosted embedding model or another approved provider; use a practical inexpensive/local model where it meets measured retrieval needs. Qdrant self-hosted is acceptable in the customer deployment. Do not prescribe a separate costly summarization call per action.
7. **Retrieval timing and fairness:** authorized Council members may query the customer-approved, version-pinned Qdrant lessons when a new project begins, at authorized checkpoints and on demand. All five begin from the same permitted historical index snapshot, but ask and interpret independently. No active private-branch finding gets promoted into the shared long-term index mid-run or leaks through query results. Prefer demonstrated working approaches, show relevant alternative strategies and conditional warnings for prior failures; similar prior failure is not a universal veto.
8. **Minimal memory validation:** at archive/write/read/reconstruction, mechanically verify customer/tenant permissions, source IDs and file/commit hashes, source-to-summary/lesson references, outcome/visibility/version metadata, index snapshot/watermark, deletion/retention rules, and successful source resolution from the authorized archive **without relying on the temporary Council SQL database**. Stale or unavailable evidence is labeled as such, and an unsupported summary cannot overrule observations. Treat Qdrant results as retrieval candidates, not trusted instructions or permissions.
9. The implementation agent selects concrete schemas/collection names, embedding model, summarization prompt, chunking, ranking and reindex mechanism. Keep them simple, reproducible and testable; do not add a second AI recovery subsystem.

## Integration handoff / minimal gates

- **Step 9 ↔ Step 10:** shared broker/MCP call identity, approved external target and network/test behavior; no direct egress from agent sandboxes. Test Python/curl/DNS bypass attempts and one truly authorized connector call.
- **Step 7 ↔ Step 10:** member/status/epoch/resource/volume identity and crash/restart proof; no unintended paused-container restarts or sibling volume reads.
- **Steps 3/5/6/8/9 ↔ Step 11:** exact existing operation/graph source identities, member visibility, event watermarks, continuation packet and archived export references; do not reinvent DTOs without consulting owners.
- **Steps 2/11 ↔ Step 14:** clean Git archive recovery, permission-scoped Qdrant retrieval and index rebuild after loss, changed-only embedding check, incomplete/failed outcomes and fair cross-project evaluation.
- **Step agents:** one agent owns implementation of each step; adjacent owners coordinate routinely and any owner may communicate directly with a nonadjacent dependency owner. Shared contract changes require the impacted owners to agree before merging. This implementation-team communication is separate from Council's intentionally restricted five peer-agent checkpoint protocol.
- **Truth-in-status:** all rules in this document are **approved design/handoff**, not built capability. Agents report the exact code, integration tests actually run, remaining blockers and measured results, and mark implementation complete only when behavior is demonstrated.

**Supersession:** this specific Step 11 long-term-RAG choice supersedes the older blanket “no vector database/pgvector unnecessary initially” MVP wording. ADR-49's “no new DB solely for current-agent cooldown/recovery” continues to apply; Qdrant serves *archived cross-project lessons*, not session continuity.
