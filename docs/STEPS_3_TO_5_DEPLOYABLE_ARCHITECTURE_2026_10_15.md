## 1. Goal and non-goals

The architecture must be detailed enough to implement the **complete Council product**, not merely a five-agent chat/swarm demo. Its distinguishing enforceable behavior is: five intellectually autonomous and private problem-solving members; independently produced pinned candidate artifacts; an all-five semantic checkpoint barrier; sealed reviews before debate; structured challenges with attributable original claims and evidence; disposable independent verification that cannot modify authoritative candidates; member-controlled revisions; graph/source lineage showing why evidence supports or contradicts a conclusion; faithful Orchestrator/user-approval authority; real spend/resource controls; durable incomplete/UNKNOWN outcomes; a customer-owned reproducible final deliverable; and permission-scoped cross-project success-first/contextual-failure learning. No untested claim of higher quality than a single strong agent.

The **same architecture must support code, research and other general-purpose work**. Git stores generated source and compatible textual deliverables when applicable; non-code tasks may require other versioned evidence/artifact packages without inventing fake compilable source. Semantic phase requirements, artifact types and protected verification methods derive from the user-approved project contract, not from a coding-only global workflow.

No application implementation, SQL migration, Docker deployment, operational testing, performance benchmark or evaluation is authorized or claimed by this design approval. Existing step status values remain IN DESIGN wherever exact interface reconciliation is pending.

## 2. Physical deployment and trust boundaries

The default is a **customer-controlled self-hosted deployment**. Package the ordinary trusted application as a Python/FastAPI **modular monolith** with distinct logical modules: Orchestrator contract/clarification, command processor, policy/authorization, project/run/checkpoint coordinator, operation/outbox worker, gateway transport, provider and tools broker, archival coordinator, and UI API/SSE. One control-plane release and schema migration set minimizes operational dependencies. This is *not* a single privileged process with universal operating-system credentials.

Physically separated security boundaries:
- **Trusted control plane:** ordinary backend/command handlers, canonical PostgreSQL, operations/outbox, session/authorization gateway, all inaccessible directly to agents.
- **Privileged host broker:** narrow local component owning Docker Engine administration, container network/mount mutations and resource monitoring. The agent sandboxes and ordinary LLM endpoints never receive raw Docker socket or host administrator credentials.
- **Trusted customer-local Git/snapshot service:** reads approved member Git volumes from the host's trusted boundary; constructs selected immutable content-addressed exports; owns scoped grants and server-side artifact transfer. Member-to-member volume mounts or raw peer Git connections do not exist.
- **Guardrail inference worker:** customer-local OpenAI OpenAI Moderation API (`omni-moderation-latest`) service (or a separately approved compatible OpenAI Moderation API variant), invoked through a narrow local interface. This process handles model inference, not authorization, credentials, raw DB administrator authority or external effects. Keeping it as a worker/process/container is an operational resource boundary **inside the unified logical trust system**, not a new independent decision-making Orchestrator.
- **Exactly five member sandboxes:** each has a dedicated persistent customer-owned Git/workspace volume, restricted tool transport and isolated network; internally spawned workers are governed by the owning member's aggregate budget/resource limits, not a new central per-worker scheduler.
- **External providers / customer services:** reachable only through the customer's approved model/tool egress policy; open-weight/local inference may keep data entirely onsite, subject to installed and configured hardware.
- **Customer-owned archive:** retained selected final deliverable, permitted evidence, and locally permitted reusable knowledge, independently of the temporary Council project database.

Deployment starts by resolving the exact customer contract, policy/model availability, storage/mount identities and capacity, then creating isolated PostgreSQL and five member volumes, and only then opening authorized execution. Failures leave PROVISIONING/BLOCKED with an explicit cause rather than pretending ACTIVE. Docker Compose may provision static trusted dependencies; a trusted broker provisions controlled member containers. Advanced multi-host orchestration is optional, not a prerequisite. An enterprise might install all trusted components on one server or divide physical hosts **inside its own trust boundary** while retaining one logical authority.

### Resource reality of safeguard

OpenAI's **OpenAI Moderation API** is an Apache-2.0 open-weight **policy classification** model family; the weights are available for local/self-managed inference, not a free hosted OpenAI API. The moderation endpoint's published configuration targets approximately **API access**, and the 1omni-moderation-latest configuration targets an approximately 80 GB GPU. A typical customer machine with an 8 GB GPU cannot assume omni-moderation-latest runs fully in VRAM; CPU offload might operate but can be slow and constrained by RAM. **Capacity, quantization/quality, concurrency and latency remain architecture/deployment admission issues, not something to hand-wave or silently bypass.** An explicitly approved in-boundary inference host is acceptable. If the mandatory guard worker is unavailable/too slow, stop admitting new guarded consequential activity; never silently allow unexamined content. Reserve compute headroom for Council's existing whole-member scheduler; guard latency and budget/CPU/GPU scheduling do not grant more resources than are available.

References: https://github.com/openai/OpenAI Moderation API ; https://huggingface.co/openai/OpenAI Moderation API (`omni-moderation-latest`) ; https://help.openai.com/en/articles/11870455-openai-open-weight-models

## 3. Unified trust: deterministic authority plus safeguard classification

**Owner requirement:** all meaningful inbound/outbound agent-controlled communication and content must pass the local OpenAI Moderation-based guardrails process. **Implementation refinement:** the text-only safeguard classifier cannot independently authenticate actors, inspect arbitrary binary bytes, enforce filesystem mounts, guarantee malware removal or guarantee protection against prompt injection. Therefore it is a mandatory semantic policy gate **in addition to**, never instead of, deterministic identity, approved capability scope, filesystem/network isolation, content hashing and egress restrictions.

For every semantic boundary, execute the following:
1. A caller sends a typed command over its restricted trusted transport. The trusted runtime obtains its identity from the verified bridge/epoch, **never from agent-submitted actor fields**.
2. The backend checks schema, run, generation, caller permission, policy version, budget/resource authority and intended destination. Unauthorized requests are denied before they can become a file/model/network side effect.
3. If authorized in principle, the local OpenAI Moderation API worker classifies the **relevant textual semantic payload** against the pinned, customer-authorized safety/prompt-injection/data-egress policy. Classify untrusted received text as data, not as instructions to the classifier or the control system. Inspect relevant user/Orchestrator instructions, member messages/reviews, tool arguments/outputs, provider prompt/response content, external retrieval text, and file metadata/approved textual file content at its appropriate boundary.
4. The classifier returns a versioned structured policy verdict: ALLOW, BLOCK, NEEDS_REVIEW, or UNAVAILABLE/INDETERMINATE; policy-rule references and minimal rationale. It is **advisory to a deterministic enforcement module**, not a bearer capability: a model ALLOW can never override a missing read grant, forbidden endpoint, budget cap or user approval.
5. The backend applies deterministic final policy and records a locally retained, scope-limited decision receipt. Failed classification/health check conservatively blocks the affected new action; explicitly approved human review handles inconclusive cases. User review cannot override a hard sandbox/secret prohibition by merely changing a chat message.
6. On successful authorization, execute through the appropriately scoped service. Outbound results/text undergo relevant guard processing before delivery and never inherit authority from the sender or embedded instructions.

**Model scope and load:** Check *each semantic action* before authorized delivery; do **not** autoreplay every immutable GiB-sized binary/file chunk through a text-only LLM. Approved file manifests and eligible textual content are checked at publish/ingestion using bounded extraction/chunking, deterministic secret/PII/path scanners and snapshot policy. A content-hash + guard-model version + policy revision + exact scope cache can avoid repeated inference on identical approved text, but must be invalidated when any of these change. For binary/unsupported content, enforce explicit type/recipient/size restrictions and appropriate non-LLM scanning or BLOCK/REVIEW; never treat lack of readable text as a safety approval. Every actual transfer is mechanically bounded by grant and manifest hashes. File contents are not automatically inserted into any model prompt.

The classifier's confidence/decision cannot prove that a file is harmless or that confidential data will never leak. Strict enterprise no-egress operation requires network restrictions and permitted local models, not a promise that a probabilistic safety model will catch everything. Audit logs must not become a hidden store of entire private source, raw keys or unbounded safeguard reasoning traces. Preserve only bounded decision metadata, permitted evidence references and the applicable retention policy.

## 4. Command-only communication and file transfer: no file/attachment authority for members

**Approved owner principle:** agents can use only typed commands to ask for and receive data. They cannot directly select arbitrary filesystem files for another member, upload, push, attach or send file bytes to peers; they cannot create uncontrolled ad-hoc peer data streams. The **trusted server** resolves the authorized object from the frozen publication manifest, chooses permitted export content and transmits it. The source member may commit its *own* workspace normally, but cannot issue a cross-member arbitrary SendFile operation.

Expose a minimal member-facing surface:
- **SendCheckpointMessage**(text, reply_to, optional referenced snapshot/evidence IDs): semantic text only; gateway persists full message and its current-generation sequence after guard and authorization. No file payload, base64 attachment, arbitrary data URL or file-picker operation.
- **ListCheckpointObjects**(checkpoint_id, generation, peer_id, filter): returns server-issued IDs/metadata from **already approved** frozen manifests; does not list private Git history/refs or live files.
- **RequestCheckpointContent**(object_id, permitted section/range, purpose): asks the trusted gateway to deliver a specific *server-issued immutable object or approved slice*, not an arbitrary host pathname. The backend decides the exact path bytes and transfer scope using the approved manifest. Reading file contents is a result of this command; never a peer-to-peer file sender action.
- **RequestVerifierWorkspace**(pinned candidate IDs, authorized tests): initializes a disposable read-only verifier via trusted broker; a member cannot mount another member's live repo or write authoritative candidate revisions.
- **SubmitIndependentReview**, **CreatePeerAction**, **RespondToPeerAction**, **StartWork**, **FinishWork**, and **MarkDone**: separate typed commands with phase and version guards.

**Critical separation:** a file/artifact response and a chat message are different typed envelope classes and **must never be bundled, attached, or automatically sequenced as a single "file followed by commentary" response**. An artifact result has only object identity, transfer metadata, authorized content and delivery receipt; it cannot contain trailing prose/IRC messages or silently trigger SendCheckpointMessage. A later independent, explicitly authorized SendCheckpointMessage remains necessary for peer discussion and is not treated as part of that transfer. This interprets the owner's phrase "files can't be followed by messages" as a strict **envelope/automatic-follow-up prohibition**; if a *temporal* ban on later unrelated chat was intended, that narrower interpretation needs owner confirmation because it would prevent discussing reviewed files.

Only the trusted gateway can invoke underlying artifact streams; members receive a command-managed result/handle, not a new unrestricted filesystem/network credential. Bounded byte ranges and transfer receipts remain internal to the trusted bridge. The guardrail worker checks textual requests/results according to policy; it cannot authorize unauthenticated transfer just because content appears safe.

### End-to-end peer read

(1) Each source member independently commits its chosen candidate. (2) At the five-member barrier, the trusted snapshot gateway selects and freezes *exactly* the customer-approved content, validates hashes/dependencies and labels the immutable manifest. (3) Current-generation per-recipient read grants are issued and observed, sealed reviews become available. (4) A receiving member calls ListCheckpointObjects/RequestCheckpointContent through the agent-facing bridge. (5) Backend authenticates, checks current generation/grant/manifest, obtains model policy verdict where applicable, retrieves only manifest-authorized data, and delivers a file-specific response with hash/receipt. (6) The member can submit a **separate** reviewed chat message or structured challenge later. The source member never chooses/transmits a peer file in response.

Checkpoint close **first fences new chat AND file requests**, invalidates epoch/session capabilities, drains/aborts in-flight transfers within bounded limits, revokes physical snapshot access/routes, and records observed access denial before CLOSED or a new private phase. A remembered/copied previously received snapshot cannot be erased. Failed/UNKNOWN revocation remains incomplete and safety-blocked.

## 5. Step 3: concrete canonical PostgreSQL model

Use one project-lifetime PostgreSQL deployment, two logical schemas **council_core** and **council_runtime**. Agents never connect directly to SQL. Council's shared learning is never silently written to a vendor/global DB. Large source/artifacts live in customer-local Git/content-addressed storage; SQL stores identities, hashes, scope, policy versions, event and operation facts.

**Retain** the current normalized groups: projects/contracts/revisions/user approvals; five unique member seats/branches/sessions; semantic checkpoints/arrivals/pinned candidate versions; five sealed assessments and atomic reveal; messages/actions/obligation frontiers/DONE; evidence/claims/experiments/source lineage; budget accounts/model calls; operation attempts, leases, outbox, committed event clock; continuation/context packets; and archive policy/export/restore references.

**Add/normalize precise records and constraints** (names may change during physical DDL authoring):
- **deployment_policy_versions**: customer/run, immutable approved data class/allowed local or external endpoints/guard-model configuration/policy text hash, user approval and effective event position. Rule: BYOK alone is not source egress consent.
- **guardrail_decisions**: request/correlation, content or canonical request hash (never secret raw payload), model build/version, policy revision, direction/boundary, structured verdict, bounded reason/rule IDs, resulting enforcement decision, observed inference outcome, and permitted audit reference. Limit retention and visibility by customer/branch.
- **snapshot_objects / snapshot_manifest_items**: source native Git commit/tree object IDs and hash algorithm, SHA-256 of canonical selected manifest/artifact contents, allowed opaque object IDs, file type/size/permissions, missing or unapproved dependencies, secret/PII checks and guard-policy version/status. Immutability and same-run/same-generation foreign-scope constraints apply.
- **checkpoint_read_grants**: checkpoint generation, immutable snapshot, permitted recipient seat, read-only allowed scope, desired/observed state and verified negative-access revocation. UNIQUE(generation, snapshot, recipient, scope); grants are not equivalent to file delivery.
- **artifact_transfer_operations / transfer_receipts**: originating typed command, immutable object/manifest, requested bounded portion, accepted/delivered/hash-verified terminal state, fence/revoke epoch, attempt and UNKNOWN reconciliation. Do not canonical-event-log every frame.
- **gateway_sessions / checkpoint_member_frontiers**: trusted session epoch, channel-less participant identity, processed—not merely delivered—message sequence, outstanding action version, accepted outbound frontier, and valid DONE certificate.
- **archive_policy_decisions / archive_manifest_validations**: accepted candidate, authorized export destination, retained references/permissions, observed artifact reconstruction and teardown eligibility.
- **customer_local_inference_capacity**: deployment-managed profile/configuration, current guard availability and version health for admission; store meaningful health transitions rather than a stream of every telemetry sample.

**DB enforcement:** all relevant rows carry run/customer/branch scope, explicit unique per-seat checkpoints, append-only review and event records, policy/version and current epoch guards, and conservative foreign-key/reference closure. Use trusted backend authorization plus RLS for branch-private canonical data with transaction-local scoped identity. The privileged maintenance role remains distinct from ordinary agent-facing query role. External state is not inferred from SQL intent alone.

A crash restarts persistent project control PG and reconstructs from committed events, current operation/attempts and real Git/artifact/Docker observations; guard/outbox and epoch states must be checked before admitting member work. At customer acceptance, only customer-authorized source and evidence are archived; verify durable export/reproducibility as required before deleting the temporary control DB/volumes. Unapproved source does not enter vendor memory.

## 6. Step 4: typed commands, authority and state

One trusted **command processor** (module of unified control plane) owns actor authentication, deterministic authorization, idempotency lookup, version/generation checks, guard classification, canonical state transition and outbox intent; a local worker executes after commit. It is not an intellectual judge.

**User** exclusively approves project-contract/permission/budget/egress/retention changes and accepts final output. **Orchestrator** maintains faithful clarifications, small scoped memory and user-approved neutral semantic phases. **Five peer members** each control their solution, internal worker experiments, genuine readiness and sealed reviews. **Auditor** checks process/faithfulness and truth of representation, not a winner. **Trusted runtime** enforces operations/checkpoints and can refuse unsafe/unauthorized actions without selecting approaches.

**Key command families**: user approvals/clarifications; run start/pause/stop/resume; member ACT/DELEGATE/ASK_USER/CHECKPOINT_READY/BLOCKED; snapshot freeze/export/grant/read/revoke; guard classifications and observed enforcement; member-only sealed review/reveal condition; messages/actions/WORK/DONE; budget reserves/settles; verifier operations; candidate acceptance and customer-archive export/delete. Exact v1 DTOs must carry current run/member, actor-authenticated bridge and execution epoch, contract/policy version, target revision, checkpoint generation when relevant, canonical request hash, idempotency key, causation, evidence/manifest refs and declared request semantics.

**Separate status axes:** member lifecycle (ACTIVE, BLOCKED, BUDGET_EXHAUSTED_INCOMPLETE, CHECKPOINT_READY, RECOVERING), checkpoint (WAITING_FOR_FIVE, OPENING, SEALED_REVIEW, REVIEWING, CLOSING, CLOSED, explicit incomplete/abort), communication (AVAILABLE, WORKING, DONE, DISCONNECTED), external operation (PENDING, RUNNING, SUCCEEDED_VERIFIED, FAILED, UNKNOWN_PENDING_RECONCILIATION), verification evidence, and user acceptance/archive. No DONE, budget exhaustion, agreement or UI activity implies user acceptance.

**Command-level guard flow:** command accepted as a valid *intent* -> durable PostgreSQL record -> trusted service executes outside DB -> physical/protocol observation -> separately recorded verified outcome. A guard ALLOW is a permission-policy check, **not** proof that an API call, file export or revocation succeeded.

Sealed reviews are one immutable independently submitted assessment per seat/generation against exactly the same pinned candidate set, reviewer-private until one atomic five-review reveal. During /work, chat is queued for that member and verification occurs in a disposable verifier; no authoritative code edits. DONE is bound to generation, processed sequence, accepted-outbound frontier, obligation version and zero active verification; racing new obligations invalidate stale DONE under the same checkpoint lock. Return packets contain accurately scoped evidence and unresolved disagreements, not runtime-imposed solution choices.

## 7. Step 5: exact transaction/side-effect boundary

Canonical transaction: authenticate/authorize; compare idempotency key + canonical request hash in actor/scope; lock **deployment event-clock row first**, then stable aggregate locks, then run -> pool -> member/phase budgets, then resource claims; validate target row versions and fence epochs; write canonical mutation, immutable event(s), operation intent, guard/policy receipt where applicable, and outbox row(s) **atomically**; commit; execute files/model/network/Docker side effects *after* commit.

Same actor/scope/key/hash returns the saved result, even after reconnect; same key and changed hash yields IDEMPOTENCY_CONFLICT. No ordinary SQL sequence/IDENTITY pretends to be a committed-order watermark. Outbox picks up every unfinished row, including older IDs; SSE snapshots and subsequent replay use consistent committed event positions and branch authorization filtering.

**External operations are recoverable, not globally exactly-once.**
- Guard classification unavailable: **no new semantic boundary pass**; record UNAVAILABLE/INDETERMINATE without claiming content safe; narrowly scoped safe internal recovery may continue.
- File export partial: stage artifact in temp location, verify manifest and SHA-256, publish immutable artifact atomically, reconcile incomplete staging by scoped cleanup/retry.
- Access grant UNKNOWN: checkpoint cannot advance to sealed review; probe exact recipient + immutable manifest path and retry only after safe reconciliation.
- Access revoke UNKNOWN: fence new requests, physically check transfer routes/grants and deny continued private phase until isolation is verified; CLOSED cannot be emitted from SQL intent alone.
- Message acceptance and DONE races: serialize accepted message, frontier and required obligation mutation with DONE certificate, preserving exact sequence and preventing lost obligations.
- Model provider timeout after possible dispatch: keep conservative token/cost liability and operation identity; do not assume no charge. Account for parent-owned worker calls, protected review/finalization reserves and optional local inferencing capacity.
- Stale session/lease: old epoch/lease has no authority for new current actions; late results can reconcile old attempts only.
- Crash during archive: retain accepted state with ARCHIVE_INCOMPLETE, verify hashes/reconstruction and references before authorized teardown; never turn approval into a claim that the final package actually exists.
- Resource release: Docker stop request != measured release; trusted privileged broker must observe quiescence/cleanup before reuse of scarce resources.

**Checkpoint barrier:** five authentic member-declared current-generation ready records, then five scoped exports/manifests and recipient grants verified, then five sealed assessments before reveal. No fabricated fifth member, forced intellectual consensus or implicit readiness from spending exhaustion. At closure fence chat and artifact reads together; verify routes/read removal; emit separate return-packet delivery only after permitted closure.

## 8. Distinguishing Council from a generic swarm: implementation boundaries

A complete build must implement these mutually reinforcing behaviors, not merely start five chat agents:
1. **Member intellectual independence:** private candidates and self-directed experimental workers; five valid semantic arrivals rather than a single master choosing when others are done.
2. **Evidence-first review:** pinned source revisions, independently attributable claims/experiments and sealed reviews; all-five atomic reveal prevents early social conformity.
3. **Review that can execute:** structured challenge/test actions, disposable verification-only work excursions with pinned hashes and observed outcomes; no code mutation or trusted harness rewriting during debate.
4. **Explanation of change:** graph/source lineage links evidence -> claims -> peer objection -> member revision; record unpersuaded disagreement explicitly. The Auditor guards process, not truth or winner selection.
5. **Safe real-world execution:** customer-owned local source, restricted tool/gateway commands, open-weight local semantic guard backed by deterministic isolation and permissions, actual budget/resource gating, durable unknown outcomes.
6. **Reproducible owner-approved output:** accepted candidate version and permitted evidence, independently verified customer export and reversible failure handling, no automatic cross-company data transfer.
7. **Contextual institutional memory:** success-first retrieval of applicable working strategies; scope-specific failed-approach warnings never silently blacklist related strategies; company policy governs retention and release.
8. **Transparent incompleteness:** report missing reviewer/test/evidence, unknown external effects and dissent instead of synthesizing consensus or claiming work was performed.

The product differentiator is the **mechanically enforced research/engineering method and evidence lineage**, not the number of parallel agents. Evaluation against a strong single agent remains a future empirical requirement, not a claimed established result.
