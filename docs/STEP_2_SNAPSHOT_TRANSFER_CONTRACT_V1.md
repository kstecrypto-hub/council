# Step 2 — Customer-local snapshot, typed peer read and grant protocol v1

**Contract status: DESIGN-SPECIFIED (2026-10-19); application NOT STARTED; runtime/security tests NOT RUN.** This is the concrete interface for the approved [local-Git Step 2](STEP_2_CUSTOMER_LOCAL_GIT_CHECKPOINT.md), [Steps 2–8 crosswalk](STEPS_2_TO_8_CROSS_STEP_RECONCILIATION_2026_10_19.md), and [Step 3–5 contracts](STEPS_3_TO_5_EXACT_INTERFACE_CONTRACT_V1.md). It is **not** a deployed service. The existing single trusted control application and its restricted host-side snapshot broker own every operation; no public GitHub, separate transfer service, direct member sockets, or new queues.

## 1. Trust and object placement (normative)

- One customer/deployment and run own five stable member seat IDs and **five separate member-private native Git repositories** in persistent, scoped member mounts. Source from non-code projects is a customer-owned evidence/artifact store with the *same manifest rules*, not a fictitious Git repository. A member never mounts another member's repository.
- The trusted snapshot broker owns a customer-local immutable content-addressed export store, isolated from member writable volumes. A manifest is scoped to \`(deployment_id, run_id, checkpoint_id, checkpoint_generation, source_seat_id)\`; for final-phase integration/re-review the \`purpose\` is separately \`INTEGRATION_SOURCE\` or \`INTEGRATED_REVIEW\` and exact Blueprint/output generation replaces checkpoint review target.
- Materialized object identity is \`(snapshot_id, opaque_object_id, sha256, byte_length, media_type)\`, never an arbitrary peer path. \`snapshot_id\` binds a canonical manifest SHA-256 over a deterministic UTF-8 JSON serialization with sorted object IDs and stable field order. Pin the source commit/tree hash and hash algorithm **when Git applies**. Do not expose unpublished parent history, refs, .git metadata, secrets, working tree dirt or credentials.
- All object IDs and cursor/transfer handles are server-issued unpredictable values scoped to one recipient and current execution/grant epoch. The member request never supplies a host file path, external URL, filename used for broker path lookup, tenant authority or peer-issued transfer credential. The backend derives actor identity from the authenticated bridge.
- The trusted backend selects required scans/egress checks and **customer-authorized** OpenAI hosted Moderation API calls for eligible text/images; moderation is not an arbitrary custom-policy or binary scanner. Unsupported media requires explicit allowlisted type/size/policy and applicable mechanical scanning or denial/review. The moderation service is not local; no customer data leaves the deployment without a current approved data-class and provider destination scope. Unavailable required safeguards fail closed **for new affected operations**, not by inventing an ALLOW.

## 2. v1 typed command envelope and operations

Use the existing Part 4 envelope: \`protocol_version="council.v1"\`, \`command_id\` UUID, \`idempotency_key\` scoped opaque string, \`run_id\` UUID, \`expected_state_version\` positive integer, \`target_type\`, \`target_id\`, \`target_generation\` positive integer, and typed \`payload\`. Authenticated actor/seat/epoch are taken from the trusted session, not caller-supplied. Existing bridge returns \`receipt_id\`, server-assigned canonical \`event_position\`, \`effective_state_version\`, \`status\`, \`correlation_id\`; a replay of the **same key + canonical payload** returns the prior committed result and a different payload with the same scoped key is \`IDEMPOTENCY_CONFLICT\`. New accepted commands require current authorization and expected version.

| Command | Authenticated actor / precondition | Required payload / reply |
| --- | --- | --- |
| \`ListCheckpointObjects\` | original seat with OBSERVED_ACTIVE scoped grant and current review/checkpoint generation | \`snapshot_id\`, \`purpose\`, optional server-listed \`parent_object_id\`, \`page_size\`, \`cursor\`; reply sorted \`[{object_id,display_name,kind,media_type,byte_length,sha256,dependency_state}]\` and bounded next cursor |
| \`RequestCheckpointContent\` | same, plus requested object explicitly in selected manifest and policy allows content | \`snapshot_id\`, \`object_id\`, \`purpose=READ/VERIFY\`, \`offset\`, \`length\` (non-negative bounded integers), \`expected_sha256\`; reply is artifact-only typed metadata + scoped transfer token/frames, never text chat |
| \`CancelContentTransfer\` | initiating recipient or trusted runtime | \`transfer_id\`, \`expected_transfer_version\`; reply terminal cancellation/UNKNOWN receipt, not proof remote effects undone |
| \`RequestVerifierWorkspace\` | reviewer during permitted bounded checkpoint \`/work\` | exact reviewed manifest IDs, authorized verifier task/test IDs; backend provisions disposable read-only inputs and isolated scratch, not source-writable mounts |
| \`SendCheckpointMessage\` | member in allowed shared-discussion state (not sealed review, not executing \`/work\`) | text, optional reference IDs; **no file bytes, attachments, content handles, auto-follow-up messages or arbitrary peer filesystem path** |

No member-facing \`SendFile\`, \`AttachFile\`, remote URL fetch, arbitrary \`ListDirectory\`, raw Git clone/checkout of peers, or direct peer-to-peer transfer exists. A later **independently submitted** chat command may discuss a file; the file result does not contain or trigger chat by itself. This resolves the owner's "files cannot be followed by messages" as **no coupled/automatic file-and-message envelope**, not a permanent ban on separately authorized discussion.

## 3. Exact snapshot and object manifest validation

One immutable manifest records:
\`schema_version, deployment_id, run_id, purpose, checkpoint_id?, generation, source_seat_id?, approved_contract_revision_id, approved_source_policy_version, source_kind(GIT_TREE|ARTIFACT_BUNDLE), git_oid_and_algorithm?, root_sha256, created_at, objects[], dependency_graph[], recipient_scopes[], scan_receipts[], missing_or_rejected[]\`.

Each object has \`object_id, canonical_relative_path_or_artifact_ref, type(FILE|ARTIFACT|SYMLINK_DESCRIPTOR), sha256, byte_length, media_type, permitted_scopes[], executable_bit?, source_oid?, dependencies[]\`. Paths are **broker-owned manifest metadata**, not selectors from a member request.

- Normalize relative paths as UTF-8 with '/' separators, reject absolute/drive/device/UNC paths, \`.\` or \`..\` components, NUL, control characters, ambiguous Unicode/case collisions on the target platform, special devices, unauthorized mount crossings and path escapes. Do not resolve symlink paths into private mounts. Symlinks are excluded by default; an explicitly approved inert descriptor may record the target string but never grant traversal. Ignore Git object metadata that is not selected by manifest.
- Include a reproducible closure: ordinary files, pinned required lockfiles/config, exact LFS object digest **if already approved and locally present**, pinned submodule revision **only as approved inert reference or a separately authorized/hash-verified selected export**, and all approved external artifacts. Neither LFS nor submodule entries trigger auto-fetch/network egress. An unresolved required reference yields \`MISSING_DEPENDENCY\` and stops verified publication, not a partial-success manifest.
- Export in staging, scan selected content/metadata under policy, compute each SHA-256 from actual bounded bytes, validate referential closure, and atomically publish a read-only exported manifest (no writer token) and independently observed \`VERIFIED\` state. If the underlying member source changes after snapshot pin, the published selected export **remains the exact older immutable snapshot**.
- Keep full selected content in customer-controlled storage with permitted retention; prevent accidentally logging raw files, secrets, moderation prompt bodies or full private source. Model text/metadata cannot assert export verification.

## 4. Bounded transfer wire protocol

Transport frame is typed \`ContentFrameV1\`:
\`transfer_id, object_id, snapshot_id, grant_id, grant_epoch, transfer_epoch, offset, bytes_length, chunk_sha256, payload_bytes, end_of_range\`.
The start receipt adds \`full_object_sha256, object_byte_length, requested_range, accepted_range, chunk_limit_bytes, policy_version, expires_at\`. Transport bytes cannot be embedded in a \`SendCheckpointMessage\` or an ordinary UI event.

- Initial **configurable** bounded engineering defaults: at most **1 MiB/frame**, **8 MiB/read command**, **1000 objects/list page**, plus per-run byte/storage quotas and applicable source/object size policy. These numbers constrain memory/transport, **not** project data size: authorized larger objects are read via multiple separately guarded ranges. No fixed count of member workers or mandatory reasoning time slice is introduced. A deployment may lower limits; higher values require approved resource/egress policy.
- Ranges must satisfy \`offset >= 0\`, \`length > 0\`, \`offset + length <= authorized object's byte_length\`, no integer overflow, and both length and page size within current cap. Cursor binds exact snapshot/grant/generation/filter/sort and expires with grant. Client-visible progress is not canonical file delivery.
- Before each accepted transfer and each chunk, recheck the current grant, auth epoch, object inclusion, scope, policy revision and transfer fence. Server verifies content against original immutable manifest full-object digest (and per-frame digest) before claiming verified bytes. Recipient checks per-frame hash and ordered offset/length; a completed bounded range is only \`DELIVERED_VERIFIED\` after signed receipt/ack of all expected bytes. A missing frame, disconnect, partial hash failure or grant loss yields PARTIAL/UNKNOWN and no completion.
- A retry of the same transfer command resumes only an already-authorized unexpired **exact same manifest/range/recipient** after checking receipts; otherwise a new grant/command is required. Transfer resume is *not* permission renewal. Avoid per-frame SQL canonical events; record command-level start, completion/failure, bytes and evidence digest only.

## 5. Grant/read/revocation states and atomic boundary

States for broker operations: \`INTENT_RECORDED -> DISPATCHED -> OBSERVED_ACTIVE | REJECTED | UNKNOWN\`; for close \`REVOKE_INTENT_RECORDED -> REVOKING -> OBSERVED_REVOKED | UNKNOWN\`. \`EXPIRED\` is **a denial of further access**, not proof physical routes/mounts were removed. Successful read requires current \`OBSERVED_ACTIVE\`, exact permitted object/scope/epoch and absence of a revocation/fence.

1. Under existing Step 5 committed-event-clock-first transaction, record one immutable per-grant intent, recipient/generation, idempotent operation, outbox and canonical state. The broker executes grant/read/revoke **outside** PostgreSQL locks, and confirms actual effect with a trusted read and negative-access/isolation probe.
2. A checkpoint only reaches SEALED_REVIEW after all-five legitimate arrived snapshots and all required recipient selected grants are **observed active**. Do not infer this from grant requests, member-reported access or a bare successful database insert.
3. On CLOSING, first atomically fence all new peer messages, object listings, content reads and verifier admissions under checkpoint generation and session/epoch. Then cancel/drain in-flight transfers with bounded policy, revoke grant handles/route/mount authorities, and separately observe no new unauthorized access. Unknown revocation prevents CLOSED and next private writing; previously read content cannot be made unknowable.
4. Separate final-stage purpose grants for Blueprint Integrator and exact integrated-result re-review are issued only after the previous checkpoint/grants have **observed** revocation. An Integrator crash/source-grant expiry blocks dependent new reads until fresh current authorization and observed scope; it never silently extends or reuses a stale grant.
5. Crash or lost response after any external effect is \`UNKNOWN_PENDING_RECONCILIATION\` until trusted effect-specific probe; never manufacture completion or replay a potentially unsafe write merely because a timeout occurred. Docker mounts are provisioned with no member access to the broker/daemon socket.

## 6. Configurable rejection codes and acceptance design

Use current Part 4/5 error envelope with stable codes: \`INVALID_SCHEMA\`, \`UNAUTHENTICATED\`, \`FORBIDDEN\`, \`POLICY_EGRESS_DENIED\`, \`MODERATION_UNAVAILABLE\`, \`STALE_GENERATION\`, \`VERSION_CONFLICT\`, \`OBJECT_NOT_IN_MANIFEST\`, \`MISSING_DEPENDENCY\`, \`SCOPE_DENIED\`, \`GRANT_NOT_OBSERVED\`, \`GRANT_EXPIRED\`, \`REVOKE_UNKNOWN\`, \`PATH_REJECTED\`, \`HASH_MISMATCH\`, \`RANGE_INVALID\`, \`TRANSFER_PARTIAL\`, \`IDEMPOTENCY_CONFLICT\`, \`RECONCILIATION_PENDING\`. Authorization failures must not leak whether a hidden object or another tenant exists.
