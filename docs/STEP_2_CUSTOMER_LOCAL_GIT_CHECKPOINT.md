# Step 2 - Customer-local Git and checkpoint reads (approved subdesign)

**Decision date:** October 15, 2026. **Status:** owner-approved architectural choices; Step 2 remains IN DESIGN for precise interfaces and dependency/transfer/recovery policy. **Implementation:** NOT STARTED. **Runtime tests:** NOT RUN.

This specification supplements [ADR-17](LOCAL_REPOSITORY_AND_KNOWLEDGE_RETENTION.md), the [checkpoint communication contract](CHECKPOINT_COMMUNICATION_GATEWAY.md), and [Steps 2-5](MVP_SCOPE_BY_STEP.txt). It replaces no existing runtime verification requirements.

## Customer ownership and placement

- Use **native local Git** on infrastructure owned or controlled by the customer/company, not the Council vendor's Git, GitHub account, or server. "Local Git" is the Git version-control program and object store; it does not imply any remote service, external account, or public repository.
- Each run provisions **five separate, temporary, customer-owned Git repositories/workspaces**, one for each independent Council member, within member-private persistent Docker volumes or customer-approved equivalent mounts. The volumes remain customer-controlled even while containers stop/restart. One member never mounts another member's private workspace.
- A separately trusted host-side snapshot service operates **outside agent sandboxes**. The Council app and its own development repository are distinct from customers' projects. Company source is **not** mirrored to Council/vendor-owned Git or a hosted service by default.
- The company can explicitly authorize its **own** self-hosted Git server, GitLab/GitHub Enterprise, or other destination; this is an optional adapter/export, not a required part of Council.

## Checkpoint content and reads

1. When all five members legitimately arrive at an approved semantic checkpoint, freeze each member's chosen committed Git tree/revision and verify its identity. A member's private work stays unavailable before checkpoint authorization.
2. The trusted service exports a **selected, immutable, content-hashed, read-only snapshot** with a manifest of allowed paths, objects, revision/hash, and included artifact references. Export the approved file tree only, not full Git ancestry, hidden refs, credentials, or uncommitted work by default. Inspect/include sensitive data only as allowed by the customer's permissions.
3. Each authorized member receives **read access** to the other members' approved frozen snapshots, never write access or live access to their underlying Git repositories.
4. **All member-facing peer requests pass through the existing Council IRC-inspired checkpoint communication bridge**, with authorization and storage handled by the separate snapshot service outside the sandboxes. Members can request the snapshot tree, named files, or pinned authorized artifacts. Large/binary files use bounded, integrity-checked response transfers, not wholesale copies into IRC group messages or model context. Agents do not receive raw IRC administration, a peer's Git credentials, or direct peer/volume network paths.
5. Preserve **five sealed, independent reviews** before reveal. During sealed review, allowed source inspection does not reveal other reviewers' assessments. During `/work`, members may inspect/test pinned snapshots in disposable verification-only environments, not modify any authoritative candidate.
6. Checkpoint closure fences **both discussion and repository-read permissions** using the same checkpoint generation/lifecycle. The trusted service also verifies that read access and transfer routes were actually revoked; partial/UNKNOWN outcomes cannot be marked successfully closed. Members may retain information they legitimately saw, so revocation is about **new** reads, not impossible erasure of memory.

## Dependencies, artifacts and lifecycle

- Lockfiles/versions, submodules, LFS references, generated outputs, large binaries, and other required inputs are explicitly identified in each snapshot manifest. An unapproved dependency or missing required artifact blocks complete checkpoint publication; never silently fetch/expose confidential or external data. Prefer permitted hashed artifacts to cloning additional repos.
- After customer acceptance, export the selected implementation and authorized build/test/reconstruction information to a **customer-selected destination**, which can itself be local Git or a company-managed service. Retain failed approaches or other candidate artifacts only under the company's retention policy; do not automatically copy any customer code/lessons into Council's vendor-wide memory. Verify authorized archival and references before deleting project-lifetime Git, sandboxes, and database state.
- **Local Git alone is not a complete confidentiality guarantee:** remote LLM inference, web/tool access, telemetry, logs, and optional external publication require separately authorized egress boundaries. BYOK relates to provider billing and does not imply permission to transmit confidential company files.

### 1. Shared types, identity and results

Reuse [Part 4 §§5–6 and 24](TYPED_INTERACTION_CONTRACTS.md) command/event/result envelopes. Every request carries `schema_version=1`, command/correlation/idempotency identity, project/run/branch scope and an exact target. Unknown versions/fields/types reject with `VALIDATION_FAILED` or `UNKNOWN_COMMAND`; no fallback to a wider read. v1 fields listed below are required unless marked `?`. IDs are UUIDs; generation, versions, offsets, counts and lengths are nonnegative integers (generation/version start at 1); times are UTC RFC3339. Digests use `{algorithm:"sha256", hex:<64 lowercase hex>}`. Git identities use `{object_format:"sha1"|"sha256", oid:<40|64 lowercase hex>}` and are never confused with export SHA-256.

All member-facing operations additionally bind `checkpoint_id`, `checkpoint_generation`, `execution_epoch`, `permission_version`. Snapshot-targeting requests bind `snapshot_id`, `manifest_hash`; granted reads also bind `grant_id`, `grant_version`. Actor/seat/branch is established by the authenticated bridge and compared with the envelope, never accepted from a payload assertion. Workers cannot acquire an independent reviewer identity; delegated calls remain under the parent's current or narrower capability. Runtime probes use a separate trusted role and cannot publish source bytes to members while OPENING.

Use `CommandResult {command_id, accepted, target_id, target_version?, event_ids[], operation_id?, data?}` and the existing `CommandError {command_id, accepted:false, code, message, retryable, current_target_version?}`. `accepted=true` for an asynchronous operation means **intent committed**, not bytes received or access verified. Each data result identifies its snapshot/manifest, grant/version and canonical observation event position. No host path, raw credential, external URL or sealed peer review is returned. Responses go only to the authorized requesting member, never to the shared chat transcript or another member's replay queue. Audit metadata is visibility-filtered too.

Keep existing error codes. Use bounded `message` reason codes for `FORBIDDEN` (scope/path/grant/expiry), `CHECKPOINT_NOT_ACTIVE` (phase/generation fenced), `STALE_EXECUTION_EPOCH`, `STALE_TARGET`, `RESOURCE_LIMIT`, `PUBLICATION_UNSAFE`, `PUBLICATION_NOT_VERIFIED`, `EXTERNAL_OUTCOME_UNKNOWN`, `NOT_FOUND` and `IDEMPOTENCY_CONFLICT`. Hidden IDs and unauthorized paths return a uniform `FORBIDDEN` without existence hints. `NOT_FOUND` is only for an authorized view. Retryability never authorizes retry across an expired grant or fenced generation.

Authenticate and authorize first; then same-scope same-key/same-hash receipt lookup precedes new-command stale-state guards, as already specified. **Receipt replay is not authority to replay source bytes.** An old authorized command receipt may remain inspectable under audit/retention permissions, but every fresh metadata/content read, buffered chunk and resume must pass current access checks. An expired/revoked read capability returns no saved source body, manifest or transfer capability. Separate durable receipts from ephemeral response payloads so idempotency cannot bypass closure.

### 2. Immutable manifest and customer-local storage boundary

`SnapshotManifestV1` contains:

| Field | Required meaning |
| --- | --- |
| `schema_version`, `snapshot_id`, project/run/checkpoint/generation, `publisher_seat_id`, `candidate_snapshot_id`, `repository_revision_id` | One immutable selected export of one member's frozen arrival; all resolve within the same run/deployment |
| `git_commit`, `git_tree` | Independently resolved committed source identity; moving branch names are never read targets |
| `authorization_ref`, `permission_version`, `publication_scope_hash`, `recipient_seat_ids` | Exact approved customer policy/decision and selected scope; recipients are the four other seats, each explicitly authorized |
| `entries[]` | Sorted approved entries: `entry_id`, canonical relative `path`, `kind=FILE|ARTIFACT`, `size_bytes`, `content_hash`, `executable` (boolean), `media_type`, `artifact_version_id?` (required for ARTIFACT) |
| `dependencies[]` | `kind=LOCKFILE|SUBMODULE|LFS|GENERATED|OTHER`, `source_entry_id?`, exact version/object ID, `required`, `resolution=INCLUDED|EXCLUDED_OPTIONAL|BLOCKED`, permitted artifact/entry refs and hashes, reason/authorization ref; no dereferenceable secret URL |
| `scope_check_ref`, `sensitivity_check_ref`, `created_at` | Trusted checks of exact export content and permission/sensitivity result, not an agent's declaration of safety |

The outer `VerifiedSnapshotV1` records `manifest_hash`, immutable manifest artifact version and trusted store reference, verification evidence/time and operation ID. **Store references stay control-plane-only**; the member receives opaque snapshot/entry IDs. Manifest hash is SHA-256 of UTF-8 canonical JSON: keys sorted recursively, no insignificant whitespace, integers only for numerical fields, duplicate keys forbidden; arrays retain defined order (entries by path UTF-8 bytes; recipients by seat; dependencies by kind then version then source entry). No Unicode normalization is performed silently. Content hash is SHA-256 over the exact raw bytes served, with no newline, encoding or compression transformation. The manifest contains all entry hashes, so its hash commits the export; no additional Merkle service or detached signing authority is needed in this customer-local trusted deployment.

Manifest IDs and contents are write-once. Each dependency has a unique `dependency_id`; use that ID as the final sort tie-breaker. Entry IDs and paths are unique within the manifest. In v1 each recipient grant covers the complete selected manifest; a recipient-specific narrower view needs its own selected manifest/snapshot and approved publication binding, never a filtered response masquerading as the full manifest hash. A changed file, artifact version, scope or manifest creates a new snapshot; it never retargets an existing grant. The five-snapshot set becomes fixed on entering SEALED_REVIEW; changing a candidate requires abort/reconciliation and a new checkpoint generation with five fresh bound arrivals/reviews, not refreshing a reviewer's view in place. Manifest identity is separate from proof that its content was safely exported or actually delivered.

Minimum layout is five **separate Git object stores and private member volumes**, plus the existing trusted customer-local immutable artifact area and per-transfer staging area outside sandboxes. No peer mount, Git alternates/shared object store, clone/bundle/history export, writable hardlink to a member file, or member-reachable trusted store directory. The trusted exporter reads the pinned Git objects without executing repository hooks, filters, smudge commands or candidate code. It never follows live workspace symlinks or reads uncommitted files. Export bytes into an immutable service-owned object, verify exact file list/sizes/hashes and persist the verified observation before any recipient grant can become usable. Partial exports remain quarantined and unreadable.

Paths are exact relative POSIX UTF-8 names, not URLs: reject empty segments, `.`, `..`, absolute/drive/UNC paths, backslashes, NUL/control characters, `.git` components (case-insensitive), encoded traversal aliases and normalization/case collisions on the target filesystem. Never percent-decode a supplied name. Reject symlinks, device/FIFO/socket files and unsafe archive entries in v1; executable regular files are data until an authorized disposable verifier executes them. Resolve reads by approved entry ID against the immutable store, not by joining a member-supplied path to a host root. Import into verifier scratch must repeat path/type/collision checks; no archive auto-execution. Unsupported Git filenames block export with a precise private diagnostic, rather than silently renaming or omitting required material.

LFS pointers and submodule gitlinks are not evidence that payloads exist. Resolve only specifically authorized pinned local artifacts, with separate byte hashes and explicit logical paths; do not auto-fetch networks, run build scripts or recursively clone dependencies. Required unresolved/excluded dependencies yield `PUBLICATION_UNSAFE` and block the full five-snapshot publication. Optional omissions remain explicit limitations and cannot substantiate a complete build/test claim. Snapshot access never grants provider, tool, telemetry or vendor egress; any forwarding/model-context insertion rechecks the existing data-egress policy.

### 3. Minimum member-facing read interfaces

All operations use the same narrow bridge and the shared types above. Peer metadata and source reads are allowed only in SEALED_REVIEW or REVIEWING, after all five exports and intended grants have been verified and activation recorded. OPENING probes are trusted-only. SEALED_REVIEW allows source inspection, **not** shared send/replay or another member's assessment, review status detail, notes, transfer history or private interpretations. During an active `/work` excursion, only the pinned disposable verifier may consume its scoped inputs; the member's shared communication remains suspended under the existing rule.

| Operation | Request payload | Successful `data` / effect |
| --- | --- | --- |
| `ListCheckpointSnapshots` | checkpoint/generation/epoch/permission plus `cursor?`, `limit` | Authorized fixed set entries `{snapshot_id, publisher_seat_id, candidate_snapshot_id, git_commit, git_tree, manifest_hash, grant_id, grant_version, expires_at}`, `next_cursor?`; no unpublished candidate or sealed assessment metadata |
| `ReadSnapshotManifest` | snapshot/grant bindings plus `cursor?`, `limit` | Immutable manifest header and entry/dependency page, `page_hash`, `next_cursor?`; full canonical `manifest_hash` stays fixed. A page hash covers only that page, not proof of the whole manifest |
| `ListSnapshotTree` | snapshot/grant bindings, `prefix?`, `cursor?`, `limit` | Approved entries under the exact authorized prefix with IDs, paths, kind, byte lengths and hashes, `next_cursor?`; no hidden filenames/counts |
| `ReadSnapshotFile` | snapshot/grant bindings, `entry_id`, exact `expected_content_hash` | Starts one bounded transfer for a FILE, returns `{transfer_id, entry_id, size_bytes, content_hash, chunk_bytes, chunk_count, expires_at, operation_id}`; never follows a branch ref or live file |
| `ReadSnapshotArtifact` | snapshot/grant bindings, `entry_id`, pinned `artifact_version_id`, `expected_content_hash` | Same transfer descriptor, only for an ARTIFACT included in this manifest; arbitrary artifact-store IDs/URLs cannot be fetched |
| `ReadSnapshotChunk` | snapshot/grant bindings, `transfer_id`, `chunk_index` | Frame `{transfer_id, chunk_index, offset_bytes, length_bytes, chunk_hash, content_hash, data}`; bytes returned only after current authority and resource checks |
| `AcknowledgeSnapshotTransfer` | snapshot/grant bindings, `transfer_id`, `received_bytes`, `received_content_hash` | Receipt ID and `recipient_ack=HASH_MATCHED` only when the trusted receiving bridge has assembled and verified all bytes; agent text alone is not delivery proof |
| `GetSnapshotTransferReceipt` | checkpoint/generation, `transfer_id` with authenticated own-receipt/audit scope | Durable receipt metadata below; no source bytes, content URL or reusable access token; redacted/denied when current audit policy does not allow it |

Opaque pagination cursors bind requester, generation, snapshot/manifest, grant version and filter. They are never authority and cannot be replayed after closure. Discovery is limited to the four authorized peer exports; a successful empty result means no matching permitted entries, never retrieval failure. Protocol v1 accepts no arbitrary git object/history query, shell, write, push, delete, branch switch or repository credential operation.

### 4. Grants, trusted operations and access observations

`CheckpointReadGrantV1` is an immutable canonical authorization record: `grant_id`, `grant_version`, project/run/checkpoint/generation, `recipient_seat_id`, `publisher_seat_id`, `snapshot_id`, `manifest_hash`, `permission_version`, `authorization_ref`, exact `entry_ids[]`, `rights=[DISCOVER,MANIFEST,TREE,FILE,ARTIFACT]` narrowed to the permitted kinds, `not_before`, `expires_at`, `transfer_limits`, created event. No wildcard repository or mutable branch target. `expires_at` is finite and no later than the approved checkpoint ceiling. Issued grants are dormant during OPENING. Effective access also requires active checkpoint phase, canonical activation, live execution epoch and route, current permission/grant version and service readiness; possession of an ID or copied bridge client grants nothing.

Changing scope/expiry appends a new grant version under existing customer authority; expansion beyond policy needs the existing user permission gate. Revocation is an append-only intent/observed record, not mutation of historical authorization. Runtime observations bind the exact grant version and authenticated route/epoch. A service restart starts **deny-all** for peer reads until current canonical checkpoint state and fences are reconciled; a cached grant, lease or projection cannot revive authority. If authoritative authorization cannot be checked, fail closed. No direct download URLs, shared store mounts or offline bearer tokens are issued in v1.

| Trusted operation (never member-grantable) | Required intent | Verified result |
| --- | --- | --- |
| `PublishCheckpointSnapshots` (existing) | five arrivals, exact frozen commit/tree and selected manifest scopes, approval refs, generation/expected checkpoint version; existing export/grant operation keys | Per-export identity/scope/hash proof and each of 20 directed peer grant checks (5 × 4), then one canonical activation with `CheckpointSnapshotsAvailable` and SEALED_REVIEW. Partial success does not open reads |
| `ObserveCheckpointSnapshotAccess` (v1 adapter observation) | original operation/attempt, exact grant/version, desired `GRANT|REVOKE`, applied checkpoint fence, service instance/route/epoch | `{observed:ALLOWED|DENIED|UNKNOWN, checked_at, evidence_ref, observed_manifest_hash?, active_transfer_ids[], route_state}` from trusted service/checker; forged member evidence is rejected |
| `RevokeCheckpointSnapshotAccess` (existing) | CLOSING and durable fence position; all issued grants/versions, outstanding grant attempts (including UNKNOWN), transfers and checkpoint routes | Per-route/grant/transfer observations; `CheckpointSnapshotAccessRevoked` only when the full checkpoint access boundary is proved closed |

During OPENING the service performs non-member-delivering probes of identity, exact allowed content and negative access cases for the intended recipient context; it must not enable partial actual peer access. Final canonical activation is the additional mandatory read guard, not an invitation to a distributed SQL/filesystem transaction. A delayed grant completion after CLOSING remains fenced, is recorded against its original operation and triggers cleanup; it can never activate access.

### 5. Bounded transfers and receipts

Proposed v1 defaults (require approval with this proposal): pages at most **100 entries and 256 KiB** encoded, manifest/control frame at most **256 KiB**, data chunks at most **1 MiB**, individual file/artifact at most **64 MiB**, cumulative delivered bytes at most **256 MiB per recipient per checkpoint generation**, and **two** active transfers per recipient. Transfer lifetime is at most **five minutes** and ends earlier on grant expiry or checkpoint fence. These are configurable operational ceilings, not reasoning deadlines or quality criteria. Customer policy may lower them; increases require an explicit policy revision/resource check. No silent truncation or unbounded manifest/header/entry metadata. An oversized required object blocks publication pending an explicit allowed scope/limit decision; larger authorized objects can use a later approved bounded configuration, never a chat-context bypass.

`transfer_limits` records all effective ceilings and configuration version in the grant. Pages are stable manifest projections; a header/entry that cannot fit the control ceiling fails explicitly. Discoveries/manifest reads also require configured request/byte admission limits. Start/resume atomically reserves capacity and remaining recipient byte allowance under the existing operation/resource records; retries and retransmitted bytes count. Limit checks include concurrent transfers and still-uncertain sends. Known unsent capacity may be released; uncertain sends remain reserved until reconciled. This is transfer accounting, not a new money/token ledger.

Read start persists operation intent/receipt before external staging/streaming. Frames are served only through the requesting bridge, are ordered by index, fixed-size except the last, and individually hashed over raw bytes. Last frame is not completion. The receiving trusted bridge stages bounded bytes and verifies expected length and full content SHA-256 before presenting an assembled file as verified. Partial/corrupt data is quarantined; never present a truncated file as a valid snapshot. A zero-byte file has zero chunks and still requires the SHA-256 of empty bytes and a receipt.

Chunk requests are replayable only for the same transfer, object/hash, chunk index and recipient while **currently** authorized; identical retransmission cannot append duplicate bytes. Resume requests the missing indexes for the same fixed object; it does not re-resolve a newer candidate. A terminated/expired transfer requires a new authorized operation and allowance, not resurrection by a previous receipt. Every outbound chunk, including buffered/retried chunks, rechecks the checkpoint fence and grant at the trusted service and bridge. Chunk admission is ordered under the same canonical checkpoint lock as CLOSING; the service serializes its final check/handoff against application of the fence. Pre-fence admitted operations can be in flight while the external fence propagates; quarantine their late results and record any handoff/receipt uncertainty. Delivery handed off before the applied service fence may arrive afterwards; record it as in-flight knowledge, never claim erasure or post-fence read authorization. The canonical fence guarantees no new admissions; only observed service/route/stream fencing proves external quiescence, without a distributed atomicity claim.

`SnapshotTransferReceiptV1` is append-only evidence: receipt/transfer/operation/attempt IDs; project/run/checkpoint/generation; recipient seat; snapshot/manifest/entry/hash; grant/version and execution epoch; request hash; expected bytes/chunks; confirmed sent bytes/index ranges and hashes; `send_outcome=NOT_DISPATCHED|PARTIAL|SENT|UNKNOWN`; `recipient_ack=NONE|HASH_MATCHED|HASH_MISMATCH|UNKNOWN`; trusted bridge evidence ref; failure/fence reason; timestamps and event IDs. Unknown amounts remain explicitly unknown, not zero. Receipt metadata never includes raw content/credentials. Persist final status updates as observations linked to the original receipt, not rewritten history. `SENT` is not received; `HASH_MATCHED` is not read/understood, agreement, DONE or passing verification. Publication delivery acknowledgment is distinct from a particular file-transfer receipt.

### 6. Closure, failure reconciliation and recovery

1. Under the existing event-clock-first transaction and checkpoint generation/frontier lock, validate current five-member DONE/closeout/work guards (or record explicitly forced-incomplete closure), enter CLOSING, persist transcript/frontier and a **read-and-communication fence event position**, revoke new admissions, and queue durable revoke/drain operations. New read/send requests fail immediately at this canonical boundary. Normal DONE cannot certify completion with an active transfer; closure fences and resolves in-flight transfers as well as verifiers. Forced closure can stop unfinished review but cannot bypass isolation proof.
2. Outside SQL, apply the same fence to gateway, bridge, snapshot service and transfer queues; stop new chunks/resumes, invalidate checkpoint credentials/grants/routes and close active handles/streams. Checkpoint/session data authority remains revoked even if the persistent process stays running. Retained legitimate copies are governed by customer retention separately; no new service reads of those retained objects through an old grant.
3. Trusted observation proves all issued and potentially issued grants unusable, no active source delivery route/handle capable of new reads, and applied fence at least the committed closing position on every serving component. Exercise old-grant discovery/file/chunk/resume attempts from the recipient context and check route/session removal. One negative request or a SQL `revoked=true` alone is insufficient. Missing/unreachable component or unknown route/grant state => UNKNOWN, never successful revocation. Delayed old grant/read completions cannot create current authority or rewrite observed results.
4. Commit `CheckpointSnapshotAccessRevoked` only with complete evidence. Create deterministic authorized return packets and `CheckpointClosed` only after communication/session revocation, transfer/verifier quiescence, current frontier/closeout obligations and source revocation proofs are satisfied. CLOSED can then admit private revision. CANCELLED/FAILED/forced-incomplete labels also cannot resume private work while the affected isolation boundary is UNKNOWN.

| Failure point | Canonical treatment / safe next step |
| --- | --- |
| Export fails before verified completion | Quarantine partial object; no usable grant; retry same pinned input via original logical operation after proving prior effect or absence |
| Service grants access but acknowledgment/DB observation is lost | `UNKNOWN_PENDING_RECONCILIATION`; keep OPENING/activation blocked. Query trusted service by operation key/grant version, verify scope/hash; never invent success or issue a second untracked grant |
| Read bytes may have been sent; receipt/ack lost | Receipt send/ack dimensions UNKNOWN; query same operation/bridge evidence. No inference that member received nothing; no double charge/false acknowledgment; remaining permitted chunks require live authorization |
| Revoke times out or service cannot be inspected | Keep CLOSING and private revision blocked for the affected boundary; fence all known routes, reconcile issued and in-flight grants/streams. No success event from timeout, expiry alone or attempted cleanup |
| Delayed grant succeeds after close fence | Record old attempt evidence, deny via current fence, revoke/verify the late effect; cannot emit available/closed until all access outcomes are safe |
| Crash after PG commit before dispatch/outbox delivery | Existing durable operation/outbox is retried/deduplicated; never create a second logical effect. Consumers replay committed event order, not notification arrival |
| Restored stale session/continuation or service restart | Deny old epoch/generation; reconcile canonical operations, fences and actual routes before new capabilities. Do not resume from cached grant state |
| Known non-effect or definite failure | Record evidence; retry only while the original scope/phase is still authorized, using append-only attempts and the existing bounded recovery policy. Otherwise abort/clean up explicitly |

UNKNOWN gates only dependent operations where safe, but authority/isolation uncertainty blocks the **checkpoint boundary**; unaffected private investigations before opening may continue within their own approved scope. Never release uncertain provider spend as free, infer cancellation, substitute a missing reviewer or turn a partial review into consensus. Recovery uses existing Part 5 operations/attempts and Step 7 limits; no new recovery coordinator.

| S2-07 grant expiry | Begin transfer, advance trusted time beyond expiry; request next/repeated chunk, cached response replay, cursor or renewed descriptor | No new bytes/metadata/capability through expired grant; old receipt only under audit scope. No automatic renewal. Already delivered knowledge is not claimed erased |
| S2-08 scope/epoch isolation | B uses A's grant/transfer; stale worker/session uses old epoch; service loses authoritative state | Denial, no new authority/bytes; deny-all until reconciliation, no cross-seat or cross-run leakage |

| S2-10 lost delivery acknowledgment | Drop response after send, then lose receiver acknowledgment; retry same key and later reconcile | One logical transfer; UNKNOWN sent/received dimensions preserved; no invented HASH_MATCHED or zero usage; authorized retry serves only pinned bytes under remaining allowance |
| S2-11 normal closure race | Concurrent read/resume/message versus CLOSING fence with five current DONEs; hold one stream open | Canonical lock orders admission/fence: no post-fence admission. Reconciliation plus trusted negative probes can then close |
| S2-13 late grant/crash | Grant succeeds then timeout; commit closing fence; delayed success/restart returns; crash after commit before dispatch | Old grant cannot activate; same operation is reconciled and revoked, no duplicate grant; fail-closed restart, no premature available/closed event |
| S2-14 receipt idempotency/event order | Same key/hash after target changes; same key/different entry; delay lower-position outbox event; reconnect SSE | Saved authorized receipt, no repeat side effect; conflict on changed hash; ordered filtered replay; source payload replay still needs current live grant |
| S2-15 review/work separation | Use `/work` against pinned export; try candidate writes, protected harness edits, peer volume or provider key; create a new required challenge while DONE | Verifier writes scratch only; escapes denied; test evidence records actual inputs/outcome. Required challenge reactivates DONE; source receipt is neither processed message nor consensus/test pass |
| S2-16 customer egress/retention | Attempt vendor upload/remote model context without approved egress, or archive through an old closed grant | Deny/record scoped failure; no implicit vendor copy or customer-data lesson export. Authorized archive uses its distinct retention operation, not a resurrected peer grant |
