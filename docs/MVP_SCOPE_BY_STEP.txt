COUNCIL - MVP SCOPE BY DESIGN STEP
==================================

**Owner's October 14 ADR-17/18 amendment supersedes old public-GitHub and vendor-retained customer-learning defaults.** Steps 2–5 design interfaces have been REOPENED for local snapshots, customer-controlled retention and typed gateway migration. Existing substantive design baselines remain documented, but no runtime implementation/tests exist. See docs/LOCAL_REPOSITORY_AND_KNOWLEDGE_RETENTION.md.

Purpose
-------

This file separates the COMPLETE PRODUCT architecture from the MVP that should
actually be implemented first.

The complete design is allowed to stay ambitious. The MVP is deliberately much
smaller: it exists to test the core Council hypothesis before we spend months
hardening advanced subsystems.

Core MVP hypothesis
-------------------

A small council of strong peer agents, ideally using different reasoning-model
families, can outperform a single strong coding/reasoning agent on sufficiently
difficult tasks when the peers:

1. begin independently;
2. cannot read one another's unpublished work;
3. publish at controlled checkpoints;
4. challenge/review one another's work;
5. retain logical identity across bounded sessions;
6. can execute and test candidate solutions in isolated environments; and
7. are evaluated fairly against a strong single-agent baseline.

The MVP is complete only when we can run that experiment repeatedly and measure
quality, correctness, failures, cost, latency, and resource use.

Important rule
--------------

Design the full interfaces now where doing so avoids a future rewrite, but only
IMPLEMENT the minimum capability needed for the MVP unless a harder feature is
required by an observed failure.

"Designed" below means the product-level decision is already substantially
specified in the repository. It does NOT mean application code exists. This
repository is still specification-only.


STEP 1 - RUNTIME ARCHITECTURE
Status: DESIGNED

Complete product
~~~~~~~~~~~~~~~~
- Event-driven runtime with durable state.
- Separate remote model-call capacity from local executable-sandbox capacity.
- Dependency waiting without occupying scarce execution slots.
- PostgreSQL-backed coordination, event notifications, SSE-facing activity.
- Trusted runtime/executors kept distinct from restricted agent sandboxes.
- Host-aware scheduling across CPU, memory, disk, GPU/devices, and sandbox slots.
- Support many logical agents even when only a few local workloads can run.

MVP must implement
~~~~~~~~~~~~~~~~~~
- One backend runtime capable of coordinating five fixed logical council members.
- Parallel model calls subject to a simple configurable concurrency limit.
- Separate local sandbox concurrency limit.
- Tasks can wait for dependencies without blocking all worker capacity.
- Basic pause/stop/cancel behavior.
- Durable enough state that a process restart does not erase the whole run.
- One simple event stream for UI/status updates.

Defer until after MVP evidence
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Sophisticated host-pressure heuristics.
- Multiple execution backends beyond the one needed by the MVP.
- Advanced distributed deployment.
- Sophisticated priority scoring and arbitrary time-based private-work slices are not required in the MVP; fixed seat admission order, semantic checkpoints, and phase token/cost ceilings are.


STEP 2 - REPOSITORY LAYOUT, DEPENDENCIES, AND IMPORT RULES
Status: REOPENED IN DESIGN - older public-GitHub baseline superseded by local-first ADR-17; no implementation

Complete product
~~~~~~~~~~~~~~~~
- Each Council member has a distinct **customer-owned local Git repository/workspace** boundary, not a mandatory external account.
- Private independent work until checkpoint policy allows publication.
- At approved checkpoints, the trusted **local gateway** shares only selected frozen read-only snapshots with authorized peers inside the customer trust boundary; **no internet-public repository is the default**. Optional external publication requires separate explicit authorization.
- Prior accepted projects may be copied/reused as bases or references.
- Accepted output is migrated/retained; disposable run state is removed.
- Clear backend/frontend/runtime/domain boundaries and dependency direction.

MVP must implement
~~~~~~~~~~~~~~~~~~
- One repository/worktree per council member candidate.
- Strong branch/repository separation before publication checkpoints.
- A deterministic location for backend, runtime, UI, tests, migrations, and
  shared schemas/contracts.
- No circular dependency architecture.
- A local immutable content-hashed export/grant/revoke mechanism for the approved frozen snapshot, without full Git history by default; no global public exposure required.
- Archive/finalize the accepted candidate and delete disposable sandbox state.

Defer until after MVP evidence
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Full cross-project reuse automation.
- Advanced repository archival policy.
- Multi-provider source-control abstraction.
- Elaborate monorepo/package governance if the MVP does not require it.

STEP 7 - MEMBER EXECUTION SCHEDULING, RECOVERY, AND RESOURCE CONTROLS
Status: DESIGNED - specification complete; runtime implementation NOT STARTED and acceptance tests NOT RUN
Primary specification: docs/PART_7_MEMBER_SCHEDULING_RECOVERY_RESOURCES.md

Complete product
~~~~~~~~~~~~~~~~
- Scheduling of whole Council-member work environments under host capacity limits.
- All-member semantic checkpoint barriers under staggered member execution.
- Durable runtime operations, leases, heartbeats, retries, cancellation, reconciliation for Council-controlled work.
- CPU/RAM/disk/GPU/device reservations.
- Budget reservations, protected review allowance, retry accounting.
- Resource-aware admission and deterministic seat-order scheduling; phase budgets bound authorized inference while a member occupies scarce slots.
- Recovery across crashes and uncertain side effects.

MVP must implement
~~~~~~~~~~~~~~~~~~
- Configurable active Council-member work-sandbox slots independent of the fixed logical member count.
- The Orchestrator sets outcome-based semantic phases/checkpoint criteria in the versioned Project Contract; a member, not the runtime, declares CHECKPOINT_READY.
- Each member has a configurable hard token and cost allowance per phase; consumption by delegated workers and session continuations is included in the applicable scope.
- Exhaustion of the phase allowance records BUDGET_EXHAUSTED / INCOMPLETE and durably suspends the member without fabricating readiness, /done, or acceptance. An authorized user may allocate more budget.
- A member that reaches the current checkpoint releases scarce private-work execution capacity and cannot proceed beyond the barrier.
- Checkpoint review opens only after every required Council member reaches the same semantic checkpoint.
- Checkpoint participation may be time-sliced across available sandbox slots; inactive members receive durable queued messages/actions when the same sandbox resumes.
- Quiesce and persist a member sandbox before stopping its execution container to free compute; later reconstruct the same logical sandbox from durable private state.
- Ephemeral credentials/capabilities are reissued on resume and are not retained merely because sandbox storage persists.
- A member targeted by a new required checkpoint action must be rescheduled even if it had previously reached /done.
- Eligible members are scheduled in fixed seat order 1 -> 2 -> 3 -> 4 -> 5 when slots become available, skipping members that currently require no execution; seat number conveys no authority. No mandatory periodic private-work time slice or reasoning deadline.
- Step 7 may cap remote/local inference resources but does not control the member's intellectual reasoning loop or decide substantive completion.
- Each member execution has a revocable execution epoch/bridge session; crash recovery invalidates the old epoch before any restarted member can make new external calls.
- Known in-flight external calls are cancelled where supported; uncertain outcomes use Part 5 UNKNOWN_PENDING_RECONCILIATION and are reconciled before replay.
- A trusted sandbox checker outside the agent container validates isolation/lifecycle state before restart/resume.
- PostgreSQL-backed durable queue/leasing for trusted Council-runtime operations, not central scheduling of an agent's private internal work.
- FOR UPDATE SKIP LOCKED or equivalent safe consumer leasing for those runtime operations.
- Lease expiry + heartbeat + retry attempt number for Council-controlled operations.
- Configurable max concurrent model calls.
- Configurable max concurrent local sandboxes.
- Trusted Council-host-side Docker Engine API stats/events monitoring per **whole member** sandbox, with adaptive/cgroup hard limits and configurable 2–5s samples, 80%/90% assigned-RAM soft-pressure response, WSL2/host memory and free-disk checks, and separate GPU/VRAM monitoring when supported. This policy does not guarantee preventing OOM kills and does not impose an internal worker-count cap.
- A failed/BLOCKED member remains a required logical Council seat; no silently reduced five-member barrier.
- BYOK/local-inference MVP; provider accounts bill users directly. Council-authorized budget gates are not guaranteed provider-invoice limits.
- Per-run, per-phase, per-member token/cost metering and conservative pre-dispatch reservations.
- Users approve their run/phase budgets and connect their own remote-provider API credentials (BYOK), or use compatible local models with no remote key; in the MVP providers bill users directly and Council does not run a prepaid token wallet.
- Raw user API credentials remain in trusted secret storage and only the scoped runtime model bridge may use them; they never enter agent sandboxes, repos, ordinary logs, or client-side persistence.
- Council budget gates limit authorized requests but do not guarantee provider-invoice caps; report uncertain usage/settlement honestly.
- Simple hard per-phase/member/run budgets plus a protected checkpoint/review/finalization reserve.
- User approves every project ceiling and allocation; propose configurable 70% development / 25% protected checkpoint reviews / 5% protected orchestration and finalization, splitting development equally by monetary value across five peers by default; each phase/member also needs an approved token ceiling. No silent top-up.
- Default remote cap: up to two concurrent requests per provider, further reduced by actual provider limits; initial local inference cap: one job, increased only after measured model/runtime hardware + tool-loop compatibility.
- Resource admission protects approximately 20% of host RAM as an adjustable initial target, increased when observed OS/Council overhead requires; VRAM is measured separately; under pressure stop admissions then safely quiesce work and confirm resource release.
- Infrastructure recovery: three default retries with increasing 5s/30s/120s delays; individual tool/provider operations have class-specific timeouts, never a global agent-reasoning deadline.
- Atomic dispatch: lock the Part 5 event clock first, then run -> spending pool -> member/phase accounts; reserve tokens/cost/resource claim with the durable operation and outbox before external dispatch; settle returned usage or retain uncertain liability.
- Pause uses QUIESCING_FOR_PAUSE activity and becomes PAUSED only on verified durable suspension; Resume rechecks guards; Stop enters STOPPING and becomes CANCELLED only after sufficient cleanup, otherwise FAILED. Candidate ACCEPT is a separate event/flow.

- Optional non-binding rough overall-project and per-phase token/cost estimate ranges shown with uncertainty and evidence basis; never automatically treated as a quota, top-up, or promise.
- **Whole-member** restart recovery and continuation from the member-owned persistent Docker volume plus existing canonical operations; no Council-owned per-worker task recovery service.
- Safe cancellation/pause.

Defer until after MVP evidence
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Fine-grained CPU/RAM reservation optimizer.
- GPU/device scheduler unless required by an MVP task.
- Advanced budget rebalancing.
- Multi-host distributed scheduling.


STEP 8 - AGENT LOOP, COUNCIL PHASES, AND DELEGATION
Status: IN DESIGN - approved amendments recorded; remaining design/integration work open
Core governance is already designed.

Accepted design decision 8.1 - member loop + optional experiments (October 14, 2026)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Primary working specification: docs/PART_8_AGENT_LOOP_EXPERIMENTATION_DELEGATION.md

The outer Council loop follows the Orchestrator's approved semantic phases, five independent private candidates, all-five checkpoint arrivals, sealed peer reviews, discussion and private revisions. A persistent member's **own** agentic loop reasons -> selects an authorized action -> observes/records the result -> repeats until that member reports readiness, blocking or another legitimate lifecycle outcome. The runtime does not intellectually judge readiness. Candidate readiness, checkpoint communication /done, BLOCKED and Step 7 budget exhaustion remain separate outcomes.

**Optional Karpathy-style autoresearch inside ACT**:
HYPOTHESIS -> CHANGE or ALTERNATIVE -> TEST/CHECK -> OBSERVE -> KEEP | REVISE | DISCARD | INCONCLUSIVE -> RECORD -> return to the same member's loop.

- This is a first-class **optional workflow**, not mandatory for each action, not a replacement for ordinary tools/reasoning, and not a separate AI supervisor/scheduler.
- Works for code, research, or other domains: compare baselines and counterexamples; numerical benchmarks only when meaningful, with units, conditions, uncertainty and regressions. No universal scalar score or automatic winner selection.
- Experiments retain exact hypothesis, baseline/changed source or repo SHA, environment/test/data versions, operations, results, limitations, member decision and immutable attributable evidence. Reverted/failed work retains the experiment record, not necessarily failed code.
- An authorized worker may perform a bounded experiment for its parent member; child calls use parent branch permissions and phase budget, and results return to the parent. Parent alone decides whether to integrate, revise, discard, or declare the **parent's** semantic checkpoint ready.
- Exploratory agent-edited tests are distinguishable from protected acceptance tests. Checkpoint /work may verify approved frozen snapshots in disposable verifiers only; no candidate implementation edits during review.
- The loop has no fixed model-call count, forced reasoning time limit, experiment quota or indefinite-experiment obligation. Step 7 budgets and operation-specific safety timeouts bound spend; Step 11 session rollover preserves logical member and experiment/operation evidence. A budget ceiling does not force CHECKPOINT_READY.

Accepted Step 8.2 worker autonomy and monitoring policy (October 14, 2026)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- A Council **worker** is a member-created AI subagent/process inside the member's allocated Docker sandbox, **not** a sixth Council seat or automatically another Docker container.
- Each member controls its internal worker count, nesting/delegation depth and parallel work. There is **no fixed worker-count or delegation-depth limit and no Council internal worker scheduler**. Workers use the parent's sandbox CPU, RAM, PID, storage, permitted GPU/device resources and approved model/API phase budget.
- Docker Engine API stats plus container lifecycle/OOM events drive one trusted resource-monitor component **outside agent sandboxes**. Monitor total sandbox consumption, including every child process. Docker/cgroups provide supported hard memory/CPU/PID boundaries. Separate trusted checks monitor host/WSL2 VM RAM, free storage/volume use, and optional GPU/VRAM through NVML or another supported device adapter.
- Initial **configurable** policy: 2–5-second metrics samples, warnings/limits on new brokered heavy work at about 80% of assigned sandbox RAM, stronger admission denial plus safe whole-member quiescence if pressure persists near 90%. These are heuristic thresholds, not guaranteed OOM prevention. Step 7's approximately 20% host RAM headroom remains separate and adjustable.
- The monitor controls **new trusted gateway/broker actions and entire sandbox lifecycle**, not arbitrary local process forks or individual worker scheduling. Unsafe/stale monitoring blocks additional heavy admissions; OOM events trigger durable same-member recovery rather than forced semantic readiness.
- The Docker daemon socket is never given to agent-controlled containers. Optional separately isolated child containers need a trusted scoped broker and must still count against the parent's aggregate approved resources.
- Worker-created model calls still use the trusted BYOK provider gateway and per-phase cost/token reservations; all children inherit the same or narrower authority. They cannot escape branch isolation, access raw credentials, grade Council peers, or declare their parent's CHECKPOINT_READY.
- The default shared **local inference gateway** concurrency limit in Step 7 is not a fixed cap on ordinary worker processes inside a sandbox.

Accepted Step 8.2a persistence decision (October 14, 2026)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Docker's **named volumes** (or approved persistent bind mounts) provide each member's durable private workspace, Git repo, saved notes, ordinary worker progress files and results across stop/container recreation. Fixed private volume ownership and mount isolation are required.
- Worker processes **do not continue from in-memory instruction state** after a container stops/crashes; the member's new process/agent session decides how to resume or repeat local subtasks from saved files. Docker does not provide automatic transparent subagent task replay. If progress was not persisted, no exact resume is promised.
- **No Council per-worker recovery manager, separate worker process ledger, resurrection daemon, mandatory worker result protocol, or per-worker scheduler**. Council controls whole-member sandbox stop/start/recreation and capability/budget/operation reconciliation; all external calls and consequential evidence still use existing trusted records.
- Deliberately stopped/paused/at-checkpoint/budget-exhausted member sandboxes must remain stopped; Docker `restart: always`/`unless-stopped` may not bypass the host scheduler, protected review barrier or reauthorization. Docker/container readable writable layer and tmpfs are **not substitutes for durable mounted storage**.
- Recreating a sandbox requires reattaching the exact member-owned volume, validating mount/permission/resource/isolation guard, fencing old epoch and reconciling UNKNOWN external effects before member authorization. Archive/retention/verified deletion controls still apply.

Step 8.1, 8.2 and 8.2a are accepted **subdesigns**, but **Step 8 remains IN DESIGN** for precise member action/observation, private-phase/final-candidate states, and checkpoint/finalization transition integration.

Complete product
~~~~~~~~~~~~~~~~
- Project Orchestrator produces the stable canonical project prompt, derives the
  project-specific semantic checkpoint plan, and handles prompt-consistent user
  clarification. It does not control Council reasoning or choose solutions.
- Equal peer council.
- Dynamic workers.
- Independent beginnings, scoped checkpoints, cross-examination, revisions,
  coverage review, synthesis, premortem, finalization.
- Adaptive checkpoints.
- Minority-investigation allowance and rich delegation policies.

MVP must implement
~~~~~~~~~~~~~~~~~~
- Project Orchestrator conversation -> approved Project Contract.
- 5 fixed equal peer Council members; seat number is identity only, not rank or authority.
- Prefer support for different strong reasoning-model families per seat.
- Independent start with no peer unpublished context leakage.
- Each Council member owns its distinct **local Git repository/worktree within the customer's authorized infrastructure**; no GitHub identity is needed.
- Between checkpoints, peer repositories are private.
- At least:
  * one early/mid checkpoint that makes approved **frozen read-only local snapshots** available to authorized reviewers,
    collects all five sealed reviews, then opens shared discussion; and
  * one mature-candidate full peer-review checkpoint using the same mechanism.
- Record exact opening/closing commit SHAs and the observed public-visibility window for every
  checkpoint.
- Peers may inspect pinned snapshots and test them in separate disposable verifiers; they receive no peer write/admin credentials or writable persistent reviewer mounts.
- Revoke scoped local snapshot grants and verify gateway/mount isolation before private work resumes; previously delivered knowledge cannot be made unknowable. External-public publication is optional, not default.
- Use a per-deployment Checkpoint Communication Gateway with ephemeral checkpoint
  rooms/sessions, identities, credentials, and sandbox routes.
- No direct sandbox-to-sandbox communication path.
- Persist checkpoint transcripts even though the live communication session is destroyed.
- Expose a minimal Council-controlled local message stream rather than a raw IRC socket/channel.
- Preserve immutable full logical message bodies with server timestamps/message IDs.
- Transparently fragment large logical messages into transport frames and reassemble/verify them before delivery; agents never manage chunks.
- Support agent-declared structured peer actions (question/challenge/finding/test request/test result/proposal) that reference the full original communication rather than replacing it.
- TEST_REQUEST is a communication request only and must not automatically create work inside another branch.
- Maintain an open-action queue so required unanswered actions cannot be silently skipped by /done.
- Support a minimal completion signal such as /done; exact local framing/transport remains to design.
- Allow a member to enter bounded /work excursions during a checkpoint; while WORKING it cannot communicate live, and incoming messages/actions are durably queued and replayed on return.
- Communication/execution exclusivity is per member, not global: other peers may continue discussion while one member works.
- Record bounded-work provenance and enforce a ceiling so /work cannot become unlimited checkpoint escape.
- /work uses a separate disposable verification environment with pinned checkpoint inputs; it is limited to verification activities.
- The authoritative candidate stays read-only during /work.
- Candidate implementation resumes only after the checkpoint closes.
- At checkpoint close, each member writes its own closeout and receives a deterministic return packet containing relevant actions, evidence, frozen peer snapshot references, unresolved items, and transcript references.
- Full transcripts remain retrievable but are not automatically stuffed into every later model context.
- Checkpoint knowledge is revision input, not an automatic task list or peer authority.
- Peer challenge and revision cycle.
- Unlimited **sandbox-local worker count and delegation depth**, subject to shared sandbox aggregate hard resources, protected host headroom, parent BYOK/phase spend and security boundaries; no Council scheduling of internal workers.
- Optional Karpathy-style structured experiment cycle as a member-chosen ACT workflow, with versioned baseline/change, test/evidence, explicit KEEP/REVISE/DISCARD/INCONCLUSIVE decision, persistent failed-attempt history, and no mandatory experiment count or global quality score.
- Worker-led experiment requests return attributable results only to the authorized parent branch; workers cannot declare the parent's checkpoint ready or edit protected acceptance tests.
- Structured escalation back to Project Orchestrator for requirement ambiguity.
- No direct user-to-agent natural-language guidance.
- Final candidate(s) preserved for evaluation.

Defer until after MVP evidence
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Sophisticated adaptive-checkpoint replanning beyond the initial project-specific milestone plan.
- Complex voting/agenda machinery.
- Sophisticated **separately managed cross-sandbox** worker orchestration; ordinary recursive worker hierarchies inside the parent's sandbox remain permitted in the MVP.
- Separate experiment optimizers/supervisors, fixed Karpathy time-boxes, global scalar winner-selection metrics, and complex automatic experiment-tree exploration.
- Every planned review phase if it does not affect the core experiment.

STEP 11 - CONTEXT RETRIEVAL, GRAPH RETRIEVAL, AGENT MEMORY, AND ROLLOVER
Status: IN DESIGN - approved amendments recorded; remaining design/integration work open

Accepted new design direction (October 14; ADR-17/18; integration still in design)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Customer's active project and any authorized long-term project reconstruction package stay **under customer ownership** on local/private storage. No vendor access or cross-customer reuse is implied.
- A separate Council general library can contain independently created/publicly permitted knowledge; customer-derived generalizations are **disabled by default** and require specific informed customer release approval and privacy/IP/license review.
- **Success-first retrieval:** find relevant previously working approaches/reconstruction recipes first, by matching actual objective, versions, configuration, workload, constraints and evidence. Show viable alternatives rather than only a single winner.
- **Contextual negative evidence:** failures/inconclusive experiments are linked warnings and suggested tests, **never a universal blacklist or hidden candidate exclusion** because a similar case failed. Compare the demonstrated failure mechanism and the exact conditions before saying the risk likely transfers. Even very similar tasks may deserve retesting under changed constraints.
- Memory outcomes and confidence remain conditional (SUCCESS_OBSERVED_IN_CONTEXT, FAILED_IN_CONTEXT, INCONCLUSIVE, NOT_TESTED, BLOCKED); no blanket 'approach A never works'. Keep actual evidence references only when authorized to retain or share them.
- All five members start from one permitted pinned memory/index snapshot but can independently query, interpret and experimentally reconsider prior failures. Step 11 memory ranking/index mechanics and acceptance tests are **NOT YET DESIGNED/TESTED**. See docs/LOCAL_REPOSITORY_AND_KNOWLEDGE_RETENTION.md.

Pre-design consideration
~~~~~~~~~~~~~~~~~~~~~~~~
Before designing Step 11, explicitly evaluate a shared Council-memory architecture where:
- accepted-project learning is retained durably in Git, not in the temporary Council PostgreSQL control database;
- a RAG/indexing layer provides selective retrieval over that Git-backed memory;
- every retrieved memory item remains traceable/citable to the exact Git file, commit, accepted project, and supporting evidence/test where available;
- all fixed Council members begin a project from the same pinned memory snapshot/index version, while their retrieval queries and interpretations remain independent;
- the memory snapshot stays frozen during an active project so newly discovered branch knowledge cannot bypass checkpoint isolation;
- new long-term memory is written/re-indexed only after user acceptance and archival;
- memory records preserve evidence, conditions and strength rather than universal prescriptions: SUCCESS_OBSERVED_IN_CONTEXT, FAILED_IN_CONTEXT, REPRODUCED_IN_CONTEXT, INCONCLUSIVE, NOT_TESTED and BLOCKED; do **not** use globally PROVEN/FAILED verdicts;
- both successful and failed approaches may be retained when they provide reusable evidence;
- agents can inspect the original Git-backed source behind a RAG result rather than trusting a generated summary;
- model diversity should remain a source of independent interpretation even when historical factual/empirical memory is shared.

Treat this as a design direction to assess when Step 11 begins, not as a finalized Step 11 contract.

Complete product

- Bounded sessions.

Defer until after MVP evidence
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

MVP DEFINITION OF DONE
======================

The Council MVP is done when a user can:

1. discuss a project with the Project Orchestrator;
2. approve a canonical Project Contract;
3. launch five peer agents with configurable reasoning models;
4. have those agents begin independently in private branches;
5. let them execute/test work in isolated Council-managed environments;
6. preserve each agent across session rollovers;
7. publish only scoped information at controlled checkpoints;
8. perform peer review/challenge/revision;
9. produce runnable candidate snapshots with reproducible environments;
10. inspect basic provenance, costs, tasks, reviews, and outcomes;
11. compare the Council fairly against a strong single-agent baseline; and
12. retain enough data to explain why the Council did or did not perform better.

Everything beyond this can remain in the complete-product specification until
evidence shows it deserves implementation.
