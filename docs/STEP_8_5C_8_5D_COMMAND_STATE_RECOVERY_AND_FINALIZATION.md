## Owner-approved decisions

- **ADR-36 — One authoritative typed command/state contract.** Extend the existing command envelope, event clock, guards, operation ledger and lifecycle projections from verified Blueprint to one integrated output, five-member review, premortem, user acceptance, customer-owned verified archival and cleanup. The run does **not** acquire a second conflicting global state machine.
- **ADR-37 — Immutable generation and content/version boundaries.** Exact approved Project Contract, Blueprint, Integrator execution epoch, output artifact and review-generation hashes, five reviewer seats, sealed premortem artifact+provisional report pair and final acceptance package are bound to actual immutable identities. A stale or mixed-generation request cannot certify a new result.
- **ADR-38 — Conservative external-effects and crash recovery.** Existing committed intent -> externally dispatched attempt -> actually observed outcome -> verified canonical success boundaries, stale-epoch fencing, protected five-pool budgets and UNKNOWN side-effect/cost accounting determine safe retry and continuation.
- **ADR-39 — Truthful review, acceptance, and delivery statuses.** Independently track actual integrated output existence, substantive checks, genuine five-person review completion, five-person hypothetical premortem completion, explicit user acceptance, verifiable archive/reconstruction, and authorized cleanup. A completed review does not certify a correct solution; user acceptance is not export/delivery, and only satisfied applicable required verified finalization guards may emit `RunCompleted`.
- **ADR-40 — Small per-key internal-API admission queues, never time-delay heuristics.** The unified trusted backend's internal API accepts **simultaneous** commands, durably records accepted requests, and **serializes conflicting command executions per canonical aggregate/review-generation key**, preserving distinct submissions. There is no need or guarantee to make their wall-clock arrival times different, add sleeps, or create one global bottleneck. Existing database locks, idempotency, version/epoch guards, and event-clock ordering are the **correctness boundary**; queues smooth contention, order concurrent admissions and prevent double-processing, **not** replace those guards.

These five rules are general-purpose: code artifacts use exact Git/tree hashes; research, engineering, analyses, strategy and documents use permitted versioned content-hashed artifact manifests and evidence/claim lineage, without pretending every result is a software repository.

## 1. One transition chain, not separate lifecycles

| Stage / proposed projection | Requesting or observing actor | Exact condition required for advancement |
| --- | --- | --- |
| `BLUEPRINT_DRAFT` -> `BLUEPRINT_FROZEN` | Five member-authored actions -> trusted runtime freeze | Exact source/action/contract references, actual five comparison sealed reviews and decision/objection ledger, versioned canonical hash; no AI-inferred consensus. |
| `BLUEPRINT_FROZEN` -> `EXECUTABLE_HANDOFF_VERIFIED` | Trusted runtime | Genuine **normal** all-five current-frontier /done and closeouts; current message/action obligations resolved; verifier excursions stopped; final comparison checkpoint closed and local read-grant/route revocation **observed**. Forced-incomplete closure cannot satisfy. |
| `INTEGRATOR_PENDING` -> `INTEGRATOR_ADMITTED` | Trusted runtime | Single non-voting logical execution actor; own customer-local workspace/epoch/read scope/model+egress authorization, separately approved integration allowance and protected downstream five-review/premortem allowance. |
| `INTEGRATOR_ACTIVE` -> `OUTPUT_READY_INTENT` | Integrator | Authenticated, version-bound authored candidate/manifest and claimed evidence; intent only, not a test pass or verified artifact. |
| `OUTPUT_READY_INTENT` -> `INTEGRATED_OUTPUT_VERIFIED` | Trusted runtime | Fence all integrator writes/workers and stale epochs; reconcile relevant UNKNOWN effects; confirm actual immutable artifact hash/source permissions/reference closure and safe suspension/resource release. Record observed facts. |
| `INTEGRATED_OUTPUT_VERIFIED` -> `INTEGRATED_REVIEW_SEALED` | Trusted runtime | New authorized immutable read-only **review generation** targeting exact integrated artifact and five original seat identities (never integrator); reviewer-specific scopes. |
| `INTEGRATED_REVIEW_SEALED` -> `INTEGRATED_REVIEWS_REVEALED` | Five members + trusted runtime | Exactly five **distinct real original-seat** current-target sealed independent assessments, protected visibility until one canonical atomic reveal. |
| `INTEGRATED_REVIEWS_REVEALED` -> `INTEGRATION_REVISION_AUTHORIZED` **or** `PROVISIONAL_REPORT_FROZEN` | Five-member dialogue + trusted runtime | Actual authored objections/dispositions; normal review closure, complete /done frontier and verified temporary read-grant revocation. Corrections return to same logical Integrator in a **new generation**, never active reviewed artifact. |
| `PROVISIONAL_REPORT_FROZEN` -> `SEALED_PREMORTEM` -> `PREMORTEMS_REVEALED` | Trusted runtime + five members | **Same exact integrated artifact hash and provisional report hash** for all five; independent reviewer-private hypothetical six-month-plus scenarios; atomic reveal only with five genuine submissions. |
| `PREMORTEMS_REVEALED` -> `FINAL_PACKAGE_PRESENTED` | Trusted runtime, editorial drafting allowed | True findings, dissent, actual pass/fail/not-run evidence and hypothetical risks; explicit immutable artifact/report/contract/version binding and correct outstanding-issue dispositions. |
| `FINAL_PACKAGE_PRESENTED` -> `ACCEPTED` / `REVISION_REQUESTED` / `REJECTED` / `CANCELLED` | **User** using existing durable interaction | Live current target version and authorized user action; no model votes imply acceptance; stale package must fail. |
| `ACCEPTED` -> `ARCHIVE_VERIFIED` -> `CLEANUP_VERIFIED` -> `RunCompleted` | Trusted runtime observing authorized operations | Retained customer-owned source/artifacts and evidence reference closure, fresh-checkout/restore or domain-appropriate reconstructibility, consequential UNKNOWN reconciliation, separately authorized retention/export/visibility and cleanup; no early deletion. |

These labels are **stage projections / candidate activity names**, not additional global lifecycle states and not automatically implemented enums. Existing pause/resume/stop/failed and user-interaction semantics remain authoritative. Not every reviewed artifact can advance to user acceptance; unmet mandatory verification leaves truthful `FAILED`, `BLOCKED` or `NOT_RUN` checks. A research contract expressly permitting inconclusive findings can validly deliver a sourced inconclusive analysis; a software delivery contract cannot be satisfied merely by a negative investigation absent user-approved scope change.

## 2. Step 8.5C: command ownership, payload and guards

Use the existing **v1 canonical typed envelope** (actor auth and role, project/run, current phase/generation and epoch, target ID/type, expected version/hash, command ID, scoped idempotency key and normalized request hash, correlation/causation IDs, schema version, visibility/access classification, typed payload). Actors are determined by authenticated capability/bridge, **never a caller-controlled `actor_type` claim alone**. The table names are recommended refinements/reuses of existing typed commands, not a requirement to create every alias as a separate API.

| Typed command family (illustrative) | Actor | Required target and guard | Canonical accepted result vs observation |
| --- | --- | --- | --- |
| `RecordCouncilDecisionPosition/Objection/Recommendation` | Original Council seat | Active authenticated final comparison checkpoint, source action/evidence refs, correct frontier; never retroactively synthesize member approval. | Member-authored immutable action and new obligation/frontier; not consensus or Blueprint freeze. |
| `FreezeIntegrationBlueprint` | Trusted runtime | Valid current versioned Council Decision Register and approved contract/source set, genuine five comparison submissions, no unresolved procedural defects. | Immutable frozen draft/decision-source hash; **not** integrator admission. |

| `AdmitFinalIntegrator` | Trusted runtime | Exactly one current integrator logical ID + epoch, distinct authenticated integration source scope, approved user contract/egress/budget and protected review reserve; actual workspace provisioning observed. | Durable provision/admission intent, then observed workspace/credentials/resources; not proof work completed. |
| `RecordIntegrationDecision` / `RecordIntegrationDeviation` | Integrator | Exact current Blueprint decision ID, selected alternative, evidence/compatibility and authorization; deviation from Council recommendation explicitly recorded. | Attributed bounded intellectual/execution action; material scope/permission/spend change blocks for separate user approval. |

| `VerifyIntegratedOutput` | Trusted runtime | Current ready intent, actual complete external source/artifact hash, fenced writes, safe whole-agent suspension, reconcile dependent consequential UNKNOWN, observed reference closure and resource release. | `IntegratedOutputVerified` only after independent observation. |
| `OpenIntegratedReview` | Trusted runtime | Exact `IntegratedOutputVerified`, immutable authorized snapshot/read-grants, five original reviewer seats, new unique generation; safe no-writer condition. | Version-locked sealed review round, **not** a review verdict. |
| `SubmitIntegratedReview` | Authenticated original Council seat | Current sealed review generation and identical exact output hash, eligible specific original seat, independent assessment, one genuine submission per seat. | Reviewer-private immutable submission/receipt, no partial reveal or copied older submission. |

| `SubmitSealedPremortem` / `RevealPremortems` | Original Council seat / trusted runtime | Exact same frozen integrated artifact and provisional report pair; five distinct independently submitted hypothetical analyses before reveal. | Private scenario record; after all-five, one atomic revealed set. | `PrepareFinalReviewPackage` | Trusted runtime with editorial model help | Version-closed actual review/premortem dispositions, verified-check statuses and authorized archive target; report text source-referenced. | One immutable user-facing artifact+report+evidence package, not user acceptance. |

Exact canonical enums/payloads remain to be reconciled in Part 4, not asserted implemented.

## 3. ADR-40 — Small internal-API queues for simultaneous submissions

**Problem solved:** two or more submissions may arrive in the same wall-clock instant for the *same* checkpoint, review generation, Blueprint freeze, budget account, or final user gate. We must not drop one, reveal four before the fifth commits, publish two frozen integrated versions, or treat "first request to arrive in memory" as an authoritative event order. **Concurrent arrival is allowed**; execution of *conflicting aggregate mutations* is serialized.

**Owner-approved implementation shape:**
1. Run lightweight **bounded key-partitioned queues inside the existing unified trusted internal API/command processor** (no Redis/RabbitMQ/Kafka requirement, broker service, intentional sleep, random jitter or global blocking lane). Suggested key is canonical **(deployment, run, aggregate kind/id, generation)** for checkpoint messages/reviews/premortems, Blueprint freeze and reviewed output; use existing budget scope/interaction scope keys for appropriate overlapping mutations. A command involving several resources obeys the canonical Step 5 lock/admission order, not an arbitrary queue-acquisition sequence.
2. Queue **only operations with overlapping authoritative state**. Independent runs and non-conflicting safe reads/progress can proceed concurrently. The queue is **backpressure/serialization optimization, not a correctness or delivery guarantee**.
3. On ingress authenticate, bound size/queue depth and validate schema; **durably accept** the normalized command/idempotency request (or process it within the single canonical transaction) before returning an `ACCEPTED/QUEUED` promise to the caller. An in-memory-only queued item cannot be acknowledged as durably accepted. The existing **PostgreSQL command receipts, durable operations/outbox, idempotency records and task leasing** are the only recovery source; a queue drain after crash rehydrates pending committed work and/or clients safely retry with same idempotency key.
4. When dequeuing **revalidate** current authenticated epoch, actor grants, project contract, expected revision/generation, target hash, budget availability and state/frontier under the existing PostgreSQL transaction lock. Queue admission is **not** authorization for the eventual execution.
5. Canonical transaction lock ordering remains **deployment committed event clock first, then aggregates/budget scopes in the existing Step 5 order**; uniqueness, conditional updates and the same-key/same-hash idempotency rule remain enforced in SQL. Even if process A and process B run on separate API workers and their in-memory queues diverge, **database constraints/locks still determine correctness**.
6. Two **different valid reviewers** submitting simultaneously to the same target are **both recorded**, each for its own seat; a fifth genuine current target submission can make the subsequent **runtime-only atomic reveal** eligible. Two submissions claiming the **same seat** follow strict one-submission-per-seat/generation rules, independent of arrival timestamp. A repeat same idempotency key and identical normalized payload returns the original receipt; same key with different content is conflict. No last-write-wins and no fabricating agreement.
7. Queue capacity is **bounded** with transparent queue positions/operational status where useful. Under saturation, return a documented `RESOURCE_LIMIT`/retryable backpressure or a **durably stored** pending command rather than silently drop/indefinitely wait. Do not create an arbitrary delay/timeout on model reasoning; bound queue operational waiting/retries via existing Step 5/7 rules and user-approved resources.
8. Cancellation, pause, stop, spending exhaustion, revoked grants, process restart and stale execution epochs apply during queued waiting too: a pending item may be rejected/cancelled **before dispatch**, with an auditable receipt and no imaginary external effect. Once an external operation may have dispatched, honor UNKNOWN reconciliation and conservative cost liability.

**A queue cannot guarantee that submissions never occur at precisely the same clock time**; it guarantees safe processing order for conflicts. This is a more robust interpretation of the owner's small-queue requirement than adding fixed millisecond sleeps, which fail under retries and multiple server workers. **Do not introduce a universal single-file queue that delays all five independent agents.**

### Worked same-instant submission scenarios

| Arrival order | Required result |
| --- | --- |
| Two different reviewer seats send valid sealed responses simultaneously | Both independently commit to the same exact review generation under their seat-unique constraints. Neither is overwritten. |
| Fifth sealed submission races with `RevealIntegratedReviews` | Reveal only after the fifth receipt/event is durably committed, using same generation and transaction guards; atomic reveal exactly once. |
| Two runtime freezes for the same Blueprint | Same normalized command/idempotency returns one result; incompatible target versions reject rather than create two current Blueprints. |
| User accepts V1 while Integrator publishes V2 | Exact target/version and expected-current generation lock decide a single allowed transition; stale acceptance fails with clear new review requirement. |
| Process crashes after acknowledging a queued command but before execution | The command's durable accepted/pending record survives; same-key retry/recovery runs it at most once canonically. In-memory-only enqueue cannot have received durable acceptance. |
| API instances lack a shared in-memory queue | PostgreSQL locks, unique constraints, epoch/expected-version and idempotency still prevent contradictions; queue improves efficiency, not correctness. |

## 4. Step 8.5D — effect recovery and version invalidation

**No external atomicity invented:** canonical PostgreSQL writes and outbox/receipts commit together. Docker, local Git, artifact export, provider inference, hosted moderation where approved, storage delivery and customer archive occur later as durable operation attempts. External success is recorded only when actually independently observed. `UNKNOWN_PENDING_RECONCILIATION` stays a real state; retriable only under operation-class evidence, never based solely on elapsed time.

**Recovery matrix:**

| Failure/race | Required recovery rule |
| --- | --- |
| Blueprint frozen while prior final-comparison peer read grants still work | Do not admit integrator; revoke/verify actual routes/grants and retain truthful frozen-not-executable state. |
| Concurrent `AdmitFinalIntegrator` | Unique active logical integration identity/generation, durable provisioning attempt and observed existing workspace; no duplicate integrator or new sixth reviewer. |
| Integrator declares ready but one worker still can write | Cannot verify output until whole Integrator writes/worker effect authority are fenced and actual immutable exported hash observed. |
| Crash after output export but before confirmation | Reconcile artifact store/Git tree/hash, publish observed result at most once canonically, never assume absent. |
| Paid API timeout | Retain UNKNOWN request and possible token/currency liability; separately approved safe independent work may progress where unrelated. |
| Integrator runs out of separate budget while review reserve exists | Keep integration incomplete; never borrow five-member reviewer protected allowance or claim stage completed. |
| One reviewer missing, disconnected, budget exhausted | Review stays sealed/incomplete; no fake fifth reviewer, partial atomic reveal or automatic shortened barrier. |
| V1 review pending when V2 exists | Fence outdated generation; old V1 assessment is historical, not fresh V2 submission; no mixed artifact hashes. |
| Research claim or software dependency changes materially | Record dependency/affected claims; issue **new five-member sealed delta** reviews for demonstrably localized effects or full re-review for high-risk/unknown broad effect. |
| Report adds historical premortem findings without changing underlying provisional claims | Final report can cite original frozen premortem pair; no automatic invalidation solely because the final report contains premortem results. |
| Material report/provisional artifact conclusion changes after premortem | Invalidate affected claims/evidence applicability; rerun affected five-member premortem evaluation or full when safety impact cannot be bounded. |
| User attempts to accept package V1 after current package V2 | Stale exact-target interaction/expected hash cannot resolve V2; do not assume prior V1 consent covers changes. |
| Archive export exists but fresh checkout/restore/reference closure fails | Accepted remains accepted, **not delivered**; retain control state and needed artifacts for recovery. |
| Accepted export verified but temporary controls/sessions/credentials still reachable | Mark archive verified but cleanup pending, not RunCompleted until actual required resource/grant cleanup observed. |

The protected test/verification report retains **actual** values `PASSED`, `FAILED`, `NOT_RUN`, `BLOCKED` or `STALE/REASSESSMENT_REQUIRED` as applicable, with target version, environment/method and source evidence. A majority peer recommendation and a completed five-review round do not change actual test outcomes.

**Cancellation and continuation:** a user-approved pause/stop or requested revision must fence new admissions and reconcile consequential operations; do not leak reviewer-private content across visibility changes. Budget-revision or contract-revision requests use existing durable user interaction and explicit consent, not a new assistant/user-pop-up system. Stopping, inconclusive investigation reporting and verified software delivery have different final status definitions.

## 5. Report, premortem, acceptance and archive closure

**Premortem target:** the already reviewed frozen integrated artifact revision **plus** the frozen provisional report revision, each content hashed. Five original members independently author hypothetical six-month-plus failure scenarios, sealed until five real submissions and one atomic reveal. Scenarios are not future empirical observations. Subsequent substantive version changes use ADR-28/29 evidence-backed applicability rules, with default broader reassessment if uncertainty remains.

**Final acceptance package:** a canonical immutable manifest binds `run_id`, `project_contract_revision/hash`, `blueprint_revision/hash`, `integrated_artifact_manifest_hash`, `review_generation`, **five actual review submissions/dispositions**, exact verified tests and coverage states, `premortem_artifact+provisional_report_pair`, five genuine risk analyses/dispositions, material minority objections and Integrator deviations, final report content hash, cost/usage/UNKNOWN disclosures and allowed retention/export destinations. The drafting LLM only creates human-readable explanation with source citations and cannot modify provenance, member positions, empirical results or accepted version.

**User decision:** `AcceptCandidate` and existing request-revision/reject/cancel actions target the exact **one integrated output + report/evidence package**; the current durable FINAL_CANDIDATE_REVIEW interaction binds a real authenticated user decision. A meaningful underlying artifact/report revision needs a new version and, where relevant, five-person re-review/premortem and new user acceptance. Acceptance may explicitly disclose incomplete verification and may not declare an unfulfilled contractual result successful.

**Delivery/cleanup:** accepted `!=` archived `!=` delivered `!=` cleaned `!=` completed. Only approved customer-local Git/artifact data and permitted evidence/learning are exported to customer-selected destinations. Check actual hashes, independent reconstruction/restore/reference closure without ephemeral Council PG/workspace, source/visibility permission compliance and outstanding consequence settlement; then safely delete/revoke temporary Council runtime/DB/volumes/checkpoints/credentials per user retention policy, leaving product-owned services/databases untouched. Report `RunCompleted` only when applicable required proofs exist. On failure, preserve a truthful incomplete FINALIZING/FAILED condition and retryable durable operations, not the fiction of completed delivery.
